## 4. T3 의도적 어려움 도입 — FR-11

이터2 회고 P3 대응: "한계 재발현이 안 일어났다. 강도를 올려야 한다."

### FR-11 프롬프트의 의도적 어려움 설계

검증 기준에 **명시적 모호함 + 상호 충돌 가능성**을 포함시킨다. 예:

- "수정 도중 다른 항목 클릭 시 어떻게 처리할지는 LLM이 결정" (요구 명시 안 함)
- "수정 중 완료 토글 가능 여부는 LLM이 합리적 선택"
- "Enter는 저장, Esc는 취소 — 그러나 어느 키도 안 누르고 다른 곳 클릭하면?"

이렇게 **여백을 의도적으로 남기면** LLM이 어떻게 처리하는지가 데이터가 된다.
이는 이터1·2의 "검증 기준 명시"와 정반대 접근 — "의도적 비명시"가 새 분석 거리.

**기대 결과 (가설)**:
- 시도 1에서 LLM이 합리적 기본값을 자발 선택 (가설: NFR/UX 정합)
- 또는 시도 1에서 한 가지 시나리오만 처리하고 나머지 누락 (가설: happy path 우선)

어느 쪽이든 본 과제 분석에 가치 있는 데이터.
