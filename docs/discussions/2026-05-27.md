## 핵심 관찰: LLM의 기존 코드 일관성 유지

오늘의 가장 중요한 발견은 다음이다.

> **LLM이 어제 만든 함수(createTask, addTask, escapeHtml 등)를 한 줄도 손대지 않았다.**

일반적으로 LLM은 "더 좋아 보이게" 기존 코드도 수정하려는 경향이 있다. 오늘 이 경향이 발현되지
않은 이유는 프롬프트에 **"어제 만든 함수와 변수명을 그대로 사용"** 이라고 명시했기 때문이다.

이게 본 과제 분석 주제 중 하나인 **"LLM이 기존 코드 일관성을 유지하는가"** 의 첫 검증이다.
검증 결과: **그렇다. 단, 명시적 가드레일이 있을 때만.**

만약 가드레일 없이 "FR-02를 추가해줘"라고만 했다면, LLM이 자발적으로 renderTaskList를 더
효율적으로 리팩토링했을 가능성이 높다. 그러면 본인이 그 리팩토링까지 검토해야 하고,
MNFR-02(100% 이해) 비용이 늘어난다.

**이 관찰이 보고서의 정량 데이터가 된다**:
- 기존 함수 수: 6개 (createTask, addTask, updateAddButtonState, renderTaskList, formatTime, escapeHtml)
- 오늘 변경된 기존 함수: 1개 (renderTaskList — 의도된 변경)
- 의도되지 않은 변경: 0개
- 가드레일 명시: "어제 만든 함수와 변수명을 그대로 사용" 한 문장
- 결과: **명시 한 문장이 5개 함수를 완전히 보호함.**

## 자발 추가 패턴의 형성

자발 추가가 어제(escapeHtml)에 이어 오늘(CSS transition)도 발생했다.

| # | 일자 | 자발 추가 내용 | 정합성 | 채택 |
|---|------|--------------|-------|------|
| 1 | Day 8 | escapeHtml (XSS 방어) | NFR-06(보안) 정합 | ✅ |
| 2 | Day 9 | CSS transition (부드러운 전환) | NFR-02(200ms 반영) 정합 | ✅ |

**공통점**: 두 자발 추가 모두 NFR과 정합한다.
**가설**: LLM이 명시적 요청 없이 추가하는 코드는 비기능 요구사항을 보완하는 경향이 있다.

이게 사실이라면 자발 추가는 일반적으로 채택해도 안전하다는 결론이 나온다. 다만 FR-12(다크모드)
같은 Won't 항목을 자발 추가하는 사례가 나오면 가설이 깨진다. 이터레이션 1 끝까지 추적한다.

## 오늘 고민한 문제 (What I struggled with)

### 고민 1: FR-07을 별도 사이클로 분리할지
**상황**:
프롬프트 원칙 3 "단일 책임"에 따르면 FR-02와 FR-07을 한 프롬프트에 묶는 건 위배다.
하지만 FR-07은 CSS 한 줄(취소선)만 추가하면 끝이다.

**선택지**:
- A. 별도 프롬프트 — 원칙 준수, 시간 낭비
- B. 한 프롬프트에 포함 — 효율, 원칙 위배 보임
- C. 한 프롬프트지만 명시적으로 두 FR을 같이 적기 — 균형

**결정과 이유**:
C 선택. 어제 이터레이션 1 계획 4장 "원칙 3"에서 이미 결정한 사항이다.
**프롬프트 원칙은 "한 가지 기능만"이 아니라 "독립적으로 검증 가능한 단위"**다.
FR-02 없이 FR-07만 만들 수 없고(완료 상태가 있어야 시각 구분이 의미 있음), 반대도 마찬가지다.
이 둘은 사실상 같은 작업의 두 측면이다.

**계획 단계의 결정이 구현 단계의 의사결정 비용을 줄였다.** 어제 정한 게 없었다면 오늘 5분 정도
"이거 묶어도 되나?" 고민했을 것이다. 미리 정해둔 덕에 0분.
이건 보고서 6.5절(종합 교훈)의 "계획의 누적 효과" 사례로 인용.

### 고민 2: 이벤트 위임을 처음 보는데 채택해도 되나
**상황**:
LLM이 이벤트 위임 패턴을 자발적으로 적용했다. 본인은 이 패턴을 처음 본다.

**선택지**:
- A. 거절하고 익숙한 패턴 요청 — MNFR-02 안전, 비효율
- B. 채택하고 학습 — 새 패턴 습득, 본 과제의 학습 효과 측면
- C. 채택하되 `// TODO: 미이해` 마커 — 정직한 절충

**결정과 이유**:
B 선택. 4단계 점검의 2번(이해)을 평소보다 길게 가져갔다.
- 버블링 단계에서 부모가 자식 이벤트를 잡는다
- `closest()`로 가장 가까운 조상 검색
- 항목 추가 시마다 새 리스너 부착 불필요

위 세 가지를 종이에 그릴 수 있을 정도로 이해함. 그래서 마커 없이 채택.

**바이브코딩의 학습 효과 측면**: 본인이 평소 안 쓰던 패턴을 LLM이 자연스럽게 노출시켰다.
프롬프트가 익숙해질수록 본인의 코드 어휘도 확장된다. 이건 본 과제의 부수 효과지만 가치 있다.
→ 보고서 6.3절(구현 단계의 교훈) "바이브코딩의 학습 효과" 사례로 인용.

### 고민 3: CSS transition을 거절할지
**상황**:
LLM이 명시적 요청 없이 `transition: background-color 0.2s ease` 같은 CSS 속성을 추가했다.

**선택지**:
- A. 거절 — 요청한 것만 받기, 범위 통제
- B. 채택 — UX 개선, NFR-02 정합
- C. 회고에서 자발 추가로 분류하고 채택 — Day 8 사례와 일관

**결정과 이유**:
C 선택. Day 8 escapeHtml과 동일 처리.
**SRS 정합성으로 판단**: NFR-02(반영 200ms 이내)와 정합 → 채택.
만약 transition이 1초였다면(200ms 위반) 거절했을 것이다. 정확히 0.2초라 한도 내.

이 결정 자체가 어제 lessons learned("자발 추가는 SRS 정합성으로 판단")의 직접 적용.
**어제 만든 교훈이 오늘 의사결정에 즉시 활용된다는 게 회고의 가치다.**

**오늘의 교훈 세 가지**:

첫째, **LLM의 기존 코드 일관성은 능력이 아니라 명시성의 함수다.** "어제 만든 함수와 변수명을
그대로 사용" 한 문장이 5개 함수를 완전히 보호했다. 가드레일을 명시하지 않으면 LLM은 자발적으로
리팩토링하려 한다. **명시는 비용이 0에 가까운 가드레일이다.**
→ 보고서 6.3절(구현 단계의 교훈) "LLM 자발 리팩토링의 제어 방법" 핵심 인용.

둘째, **자발 추가는 NFR과 정합하는 경향이 있다는 가설.** Day 8(escapeHtml)과 Day 9(transition)
두 자발 추가 모두 NFR과 정합한다. 만약 이터레이션 1 끝까지 이 패턴이 유지되면, LLM의 자발 추가가
실용적으로 신뢰 가능하다는 결론을 낼 수 있다. 단, 가설이라 데이터 누적이 필요하다.
→ 보고서 6.3절(구현 단계의 교훈) "LLM 자발 추가의 패턴 분석" 사례로 인용.

셋째, **어제 만든 교훈이 오늘 의사결정에 즉시 활용됐다 — 회고의 가치 직접 발현.**
오늘 CSS transition 채택 결정에서 어제 lessons learned("자발 추가는 SRS 정합성으로 판단")를
그대로 적용했다. 어제 일지에 적어두지 않았다면 "이거 받아도 되나?"를 5분 정도 고민했을 것이다.
**일지가 단순 기록이 아니라 의사결정 도구라는 점이 처음으로 실증됐다.**
→ 보고서 6.4절(품질 관리 단계의 교훈) "회고가 다음 사이클에 미친 영향" 사례로 인용.
