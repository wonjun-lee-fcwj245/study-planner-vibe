## 오늘 고민한 문제 (What I struggled with)

### 고민 1: "오늘"의 기준 — 로컬 타임존 vs UTC
**상황**:
오늘 항목 필터링에 `isSameDay` 함수가 필요한데, 두 시각을 어느 타임존으로 비교할지.
`createdAt`은 ISO 형식(UTC)이고, 사용자가 보는 "오늘"은 로컬 타임존이다.

**선택지**:
- A. UTC 기준 비교 — 일관성, 하지만 사용자 직관과 불일치 (자정 직전 추가한 항목이 다음날로 이동 가능)
- B. 로컬 타임존 비교 — 사용자 직관 일치, 다국가 사용자엔 혼란 가능
- C. 사용자 설정으로 선택 — 오버

**결정과 이유**:
B 선택. 본 버전은 단일 사용자, 단일 지역(한국) 가정이다. 사용자가 보는 "오늘"과 일치하는 게
가장 자연스러운 동작.

LLM이 자발적으로 `Date()` 객체의 `getFullYear/Month/Date()`로 비교 — 자동으로 로컬 타임존.
**LLM이 한국어 사용자라는 맥락에서 자연스럽게 로컬 타임존을 선택**한 점이 흥미롭다.
이건 자발 추가는 아니지만 자발 결정 — 명시되지 않은 선택을 LLM이 합리적으로 했다.

### 고민 2: 진도율 0건일 때의 표시 — "0%" vs "학습 없음"
**상황**:
오늘 항목이 0개일 때 0%로 표시하면 0/0 = NaN 위험. 또는 사용자에게 부정적 인상.

**선택지**:
- A. "0%" — 일관된 형식
- B. "학습 없음" — 부드러운 표현, 0/0 회피
- C. 카드 자체 hidden — 정보 최소화

**결정과 이유**:
B 선택. LLM이 자발적으로 "학습 없음" 텍스트 채택. 0으로 나누는 위험도 자연스럽게 회피.
A는 NaN 발생 위험을 본인이 명시했어야 함. C는 너무 정보 부족.

**관찰**: LLM이 엣지 케이스를 별도 명시 안 했는데도 자연스럽게 처리.
Day 10 FR-04에서는 누락했던 LLM이 Day 13에서는 처리. 차이점: **본 작업의 난이도가 보통**.
가설 다시 한 번 강화: "LLM은 보통 난이도에서 엣지 케이스를 자발적으로 잡는다."

### 고민 3: 진도 카드를 항상 표시할지, 조건부 표시할지
**상황**:
오늘 항목이 0개일 때 진도 카드를 숨길지 표시할지.

**선택지**:
- A. 항상 표시 — 헤더 레이아웃 일관성
- B. 항목 0개 시 숨김 — 정보 최소화
- C. 항목 0개 시 "학습 없음"으로 다른 표시 — 절충

**결정과 이유**:
C 선택. 와이어프레임 영역 A의 우측 자리는 비전이 명확하다 — "오늘 진도 한눈에 확인".
숨기면 자리가 비어 보임. 다른 표시로 자리를 유지하는 게 와이어프레임 일관성에 맞다.

이건 와이어프레임의 가치 — 작은 결정에서도 일관성의 기준이 됨. Day 5의 와이어프레임 작업이
오늘도 결정의 가드레일로 작동.
→ 보고서 5.2절 "와이어프레임이 미시 결정에 미친 영향" 사례.

## AI/팀원과의 토의 발췌

```
나: isSameDay 같은 헬퍼를 별도 함수로 빼는 게 맞아? 한 번만 쓰이는데.

Claude: 두 가지 관점이 있다.
        (1) YAGNI 관점: 한 번만 쓰니 인라인으로 충분.
        (2) 가독성 관점: "같은 날인가"라는 의도가 함수명에 명시되면 코드가 자기 설명적.

        본 작업의 경우 가독성이 더 가치 있다. renderProgressCard 안의 filter 콜백이
        ".filter(t => t.getFullYear === ...)"처럼 길면 의도가 흐려진다.
        ".filter(t => isSameDay(t.createdAt, today))"이 한눈에 읽힌다.
        
        또한 FR-09(7일 차트) 구현 시 isSameDay를 재사용할 가능성이 높다 — YAGNI도 미래를 본다.

→ 적용: isSameDay 별도 함수 유지. Day 14 FR-09에서 재사용 여부 확인.

나: 토글 시점에 renderTaskList만 호출하면 안 돼? 진도 카드까지 다시 그리면 비효율 아냐?

Claude: 비효율 정량을 따져보자.
        - tasks 100건 가정, renderProgressCard 비용: filter + Math.round = ~0.5ms
        - 사용자가 토글하는 빈도: 분당 1~2회 추정
        - 누적 비용: 분당 0.5~1ms = 사실상 0
        
        반면 "토글이 진도율을 바꾸는데 카드가 안 갱신되면" 버그다.
        성능 미세 최적화보다 일관성이 압도적으로 가치 있다.
        
        React가 자동으로 하는 "전체 다시 그리기"를 Vanilla JS에서 수동으로 흉내내는 것.
        ADR-002(프레임워크 없음)의 자연스러운 귀결.

→ 적용: renderAll() 호출 유지. 보고서 6.2절에 "Vanilla JS에서도 함수형 패턴 형성" 사례 인용.
```

첫째, **이전 단계의 결정이 후속 단계의 부담을 줄인다 (시간 누적 효과 직접 확인).**

변환 가능하게 했다. **하나의 결정이 여러 후속 결정의 비용을 동시에 낮춘다.**
→ 보고서 5.2절(정성적 분석) "설계 결정의 누적 효과" 핵심 사례.

둘째, **LLM은 보통 난이도에서 엣지 케이스를 자발적으로 잡는다 (가설 강화).** 0/0 NaN 위험을
명시하지 않았는데도 LLM이 "학습 없음" 분기를 자발 처리. Day 10(어려운 작업)에서 누락했던
LLM이 Day 13(보통 작업)에서는 처리. 가설이 4번째 데이터로 강화됨.
→ 보고서 6.3절(구현 단계 교훈) "LLM 자발 추가 ↔ 난이도 관계" 사례.

셋째, **Vanilla JS에서도 함수형 패턴이 자연스럽게 형성된다.** `renderTaskList` → `renderAll`
패턴은 React의 "데이터 → UI 단방향 흐름"과 유사하다. ADR-002(프레임워크 없음)를 채택했는데도
좋은 패턴은 도구와 무관하게 형성됨. **프레임워크는 도구이지 패턴의 원천이 아니다.**
→ 보고서 6.2절(설계 단계 교훈) "패턴은 도구를 초월한다" 사례.
