## Day 5 거절 결정의 측정 가능한 효과 발견

오늘 작업을 시작하면서 인상적인 발견이 있었다.
**자동 분배 기능을 거절한 결정(Day 5, FWC-001)이 데이터 모델 작업량을 약 1/3로 줄였다.**

만약 자동 분배를 수용했다면 오늘 설계해야 했을 엔티티들:
- `Schedule` (요일별 고정 일정)
- `TimeBlock` (시작·종료 시각, 가용 여부)
- `Allocation` (Task와 TimeBlock의 매핑 결과)

각 엔티티마다 필드 정의 + 관계 설계 + 직렬화 전략이 필요하다.
짧은 시간 안에 끝나기 어려웠을 것이고, 끝냈더라도 검증이 부실했을 가능성이 높다.

**거절 결정의 효과는 거절한 순간이 아니라 그 이후의 모든 작업에서 발현된다.**
이건 보고서에 정량적으로 인용할 수 있는 자료다.

## 오늘 고민한 문제 (What I struggled with)

### 고민 1: 단일 엔티티로 충분한가, 분리해야 하나
**상황**:
처음에는 `Task` 외에 `Subject` (과목) 도 별도 엔티티로 만들까 고민했다.
과목별 색상, 과목별 통계 같은 게 자연스럽기 때문이다.

**선택지**:
- A. `Task`와 `Subject` 분리 — 정규화, 일관성 보장
- B. `subject`를 `Task`의 문자열 필드로만 — 비정규화, 단순함
- C. `Task` + `Subject` 둘 다, 단 `Subject`는 동적 추출 (집합 함수)

**결정과 이유**:
B를 선택. C도 매력적이었지만 오버엔지니어링이라고 판단했다.

근거:
1. **본 버전에 과목별 메타데이터(색상, 정렬 순서)가 없다.** 와이어프레임에도 없음.
2. **`Set(tasks.map(t => t.subject))` 한 줄로 과목 목록 추출 가능.** 별도 엔티티 불필요.
3. **MNFR-02(100% 이해)**: 단일 엔티티가 더 단순하고 추적 쉽다.
4. **YAGNI**: 진짜 필요해지면 그때 추가 (`Subject` 엔티티를 v2.0 후보로).

데이터 모델의 "잘 짜진 정도"는 정규화 수준이 아니라 **요구사항에 맞는 단순성**이다.
이 점은 어제 와이어프레임에서 "충실도가 높을수록 좋은 게 아니다"와 일맥상통한다.
**복잡함과 좋음을 혼동하지 않는 것**이 설계 단계의 핵심 능력.

### 고민 2: localStorage 키 전략 — 어디까지 미래를 대비할 것인가
**상황**:
전략 A(단일 키)는 단순하지만 항목 수가 늘면 비효율. 전략 C(날짜별)는 통계에 유리하지만 복잡.

**선택지**:
- A. 전략 A로 시작, 필요시 마이그레이션 — 단순함 우선
- B. 처음부터 전략 C — 미래 대비
- C. 하이브리드 — 항목은 단일 키, 집계 결과는 별도 캐시 키 — 최적화

**결정과 이유**:
A 선택. 결정적 근거는 **실제 성능 측정 추정**이다.
수백 건 데이터를 `filter().reduce()` 하는 시간은 1ms 미만이다.
페르소나 1(이원준)의 6과목 × 한 학기(15주) × 일평균 3건 = 270건. 본 버전에서 도달 가능한 최대치.
이 규모에서 전략 A의 성능 문제는 발현되지 않는다.

**"미래를 대비한 복잡함"은 가장 비싼 형태의 코드 부채**다.
필요할 때 마이그레이션하면 된다. 그 시점에 더 나은 도구(IndexedDB 등)가 나와있을 수도 있다.

### 고민 3: 통계 집계 알고리즘을 지금 정의해둘지
**상황**:
FR-08, FR-09, FR-10은 모두 이터레이션 2 작업이다. 데이터 모델 단계에서 알고리즘까지 정의하는 게 과한가?

**선택지**:
- A. 알고리즘은 구현 단계(Day 12~)에 정의 — 점진성 원칙
- B. 의사 코드 수준으로 미리 정의 — 데이터 모델이 통계 요구를 만족하는지 검증 가능
- C. 실제 코드까지 미리 작성 — 오버

**결정과 이유**:
B 선택. 알고리즘을 의사코드로 미리 정의하는 행위가 **데이터 모델의 검증 도구**가 된다.

집계 알고리즘을 적어보면서 "이 필드로 이 계산이 가능한가?"를 점검할 수 있다.
예를 들어 FR-09(일별 차트)는 `completedAt`이 있어야 가능하고,
FR-10(과목별 완료율)은 `subject`와 `completed`가 함께 있어야 가능하다.

만약 알고리즘을 안 적었다면, Day 12에 "어? 이 필드가 없네" 하고 데이터 마이그레이션해야 했을 것이다.
**의사코드는 미래의 코드가 아니라, 현재 설계의 검증 코드다.**

## AI/팀원과의 토의 발췌

오늘 Claude와 데이터 모델 결정 시 토의한 내용:

```
나: Task 객체에 우선순위(priority) 필드를 넣을지 고민이야. 학습 항목마다 중요도가 다르잖아.

Claude: 두 가지 질문을 먼저 해야 한다.
        (1) 어떤 FR이 priority를 필요로 하는가? SRS 0.3을 찾아보니 priority를 다루는 FR이 없다.
        (2) priority가 화면에 어떻게 표시되는가? 와이어프레임에 priority 표시 영역이 없다.

        FR도 와이어프레임도 요구하지 않는 필드를 데이터 모델에 넣는 것은
        "있으면 좋을 것 같아서"라는 욕심이다. YAGNI 원칙 위배.

→ 적용: priority 미포함. "의도적으로 포함하지 않은 필드" 표에 사유와 함께 기록.
   priority가 필요해지는 시점은 정렬·필터 FR이 추가될 때다. 그때 다시 검토.

나: localStorage 키를 처음부터 날짜별로 나누면 통계 만들 때 편하지 않을까?

Claude: 두 가지 비용을 비교해야 한다.
        (1) 지금 복잡한 키 전략을 도입하는 비용
        (2) 나중에 마이그레이션하는 비용
        
        본 버전 규모(수백 건)에서 (1)은 (2)보다 크다.
        왜냐하면 (2)는 발생할지 안 할지 모르는 비용이고, (1)은 확실히 발생하기 때문이다.
        그리고 마이그레이션이 필요해질 시점에는 IndexedDB나 다른 더 나은 도구가 답일 수도 있다.

        "지금 가장 단순한 것 + 미래의 자유"가 "지금 복잡한 것 + 미래의 부담"보다 거의 항상 낫다.

→ 적용: 전략 A(단일 키) 채택. 단, 키 네임스페이스(`study-planner:`)는 미리 예약.
   prefix만 정해두면 미래 확장 비용이 0에 가깝다.

나: 데이터 모델 문서에 통계 집계 알고리즘까지 적어야 해? 그건 이터레이션 2 코드 같은데.

Claude: 알고리즘을 의사코드로 적는 것은 코드 작성이 아니라 데이터 모델 검증이다.
        "이 데이터로 이 통계가 만들어지는가?"를 지금 시뮬레이션하는 셈이다.
        만약 시뮬레이션 도중 "이 필드가 없네" 하고 발견되면, 지금이 바로 그것을 추가할 적기다.
        구현 단계에 가서 발견하면 마이그레이션 비용이 든다.

→ 적용: 의사코드 수준으로 3개 집계 알고리즘 명시.
   결과적으로 `completedAt` 필드가 통계에 필수임을 확인했다.
   만약 안 적었다면 `completedAt` 없이 설계하고, Day 12에 큰 변경이 필요했을 것이다.
```

**오늘의 교훈 세 가지**:

첫째, **거절의 효과는 거절한 순간이 아니라 그 이후 모든 작업에서 발현된다.** 어제 자동 분배를
거절한 결정이 오늘 데이터 모델 작업량을 1/3로 줄였다 (엔티티 3개 추가 작업 회피).
보고서에 정량적으로 인용 가능한 사례다. **"거절했더니 시간이 줄었다"가 아니라 "거절했더니
이후 모든 산출물의 작업량이 줄었다"는 점이 누적 효과의 본질이다.**
→ 보고서 5.1절(정량적 분석) "단계별 소요 시간"에 인용.

둘째, **복잡함과 좋음을 혼동하지 말 것.** `Task`/`Subject` 분리, 날짜별 키 전략, priority 필드 —
모두 "더 잘 짜진 것처럼" 보였지만 실제로는 본 요구사항에 비해 과한 복잡함이었다.
**좋은 설계는 화려한 구조가 아니라 요구사항에 맞는 단순함이다.**
이건 어제 와이어프레임에서 "충실도가 높을수록 좋은 게 아니다"와 같은 원리다.
**바이브코딩에서 특히 위험한 함정**이다. LLM에게 "데이터 모델을 잘 설계해줘"라고 던지면
대개 정규화가 잘 된 복잡한 구조를 내놓는다. 그게 "좋아 보이지만" 본 요구에 안 맞다.
→ 보고서 6.2절(설계 단계의 교훈) 인용. 바이브코딩의 한계 사례.

셋째, **의사코드는 미래의 코드가 아니라 현재 설계의 검증 코드다.** 통계 집계 알고리즘을 의사코드로
미리 적어보면서 `completedAt` 필드의 필요성을 확인했다. 이 검증이 없었다면 Day 12에 마이그레이션
비용이 발생했을 것이다. **설계 단계에서 "구현 비슷한 것"을 적는 행위는 점진성 위배가 아니라
설계의 검증 도구**다.
→ 보고서 6.2절(설계 단계의 교훈) 인용. "각 단계가 다음 단계에 미친 영향" 사례.
