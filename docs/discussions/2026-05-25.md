##  LLM 선정 결정 — Claude 웹 인터페이스 확정

### 결정 시점
2026-05-25 (Day 7) 작업 중. 본 결정은 본 과제의 모든 후속 바이브코딩 작업의 전제 조건이 된다.

### 검토한 도구 4종

| 도구 | 핵심 특성 | 본 과제 적합도 |
|------|----------|--------------|
| Claude (claude.ai 웹) | 채팅 기반, 수동 코드 복사 | ⭐⭐⭐⭐⭐ |
| Claude Code (CLI) | 터미널 통합, 자동 파일 수정 | ⭐⭐⭐ |
| ChatGPT | 보편적, 익숙함 | ⭐⭐⭐ |
| GitHub Copilot / Cursor | IDE 통합 자동완성 | ⭐ |

### 결정: Claude 웹 인터페이스 (claude.ai)

#### 핵심 근거 3가지

**근거 1: 맥락 연속성의 자동 보장**
Day 1~6 동안 작성한 모든 설계 문서(SRS, ADR-001/002, 와이어프레임, 데이터 모델)가
**이미 본 채팅 흐름 안에 누적되어 있다**. 새 도구로 옮기는 순간 모든 맥락을 다시 전달해야 한다.
이는 단순히 비효율적인 게 아니라, **MNFR-01(FR ID 인용)을 운영하기 어렵게** 만든다.

**근거 2: 프롬프트-결과 추적성**
본 과제 보고서의 핵심은 "어떤 프롬프트가 어떤 결과를 만들었는가"의 분석이다.
Cursor·Copilot 같은 자동완성 도구는 프롬프트와 결과의 인과를 흐리게 만든다.
Claude 웹은 **한 메시지 = 한 프롬프트 = 한 응답**이라는 명확한 단위가 있어 추적이 깔끔하다.

**근거 3: 수동 복사 절차가 MNFR-02의 가드레일**
Claude Code(CLI)와 비교할 때 가장 큰 차이가 이 부분이다.
CLI는 파일을 자동 수정한다 — 본인이 응답을 보지 않고 채택하는 유혹이 강하다.
Claude 웹은 응답을 읽고, 손으로 선택해서 복사하고, 에디터에 붙여넣는 절차가 자연스럽다.
**이 수동 절차 자체가 MNFR-02(100% 이해)의 운영 가드레일**이다.
의식적으로 노력하지 않아도 자동으로 검토가 강제된다.

#### Claude Code를 채택하지 않은 이유

Claude Code도 같은 LLM(Claude)이지만, **본 과제 맥락에서는 웹 인터페이스가 더 적합**하다고 판단했다.

- 자동 파일 수정은 빠르지만 MNFR-02 운영에 추가적인 의식적 절차가 필요하다
- 프롬프트 로그를 보존하려면 터미널 출력을 별도로 캡처해야 한다
- 본 채팅의 토의 맥락을 옮기기 어렵다

Claude Code 자체가 나쁜 도구는 아니다. 그러나 본 과제의 **핵심 목적이 "바이브코딩의 한계 분석"** 이라는 점을 고려할 때, 한계가 가장 명확하게 발현되는 형태(웹 + 수동 복사)가 분석 자료를 더 풍부하게 만든다.

### 본 결정의 운영 규칙 (프롬프트 전략 2.4절에 명문화)

1. 본 과제의 모든 바이브코딩 프롬프트는 Claude 웹에서 진행한다
2. 본 채팅 세션을 그대로 이어간다 (Day 1부터 누적된 토의 맥락 유지)
3. 응답 코드는 항상 수동으로 복사한다 (자동 적용 기능 미사용)
4. 각 프롬프트·응답은 `docs/prompts/`에 즉시 로그한다

### 이 결정이 보고서에 갖는 의미

본 결정 자체가 보고서 3.4절(프롬프트 전략)과 6.3절(구현 단계의 교훈)에 인용된다.

**핵심 메시지로 도출 가능한 통찰**:
> "도구 선택은 단순히 '편한 도구를 고르는 일'이 아니다. 본 과제 맥락에서 Claude 웹 인터페이스의
> '수동 복사 절차'가 MNFR-02(100% 이해)의 운영 가드레일로 작동한다는 점은 의도하지 않은
> 부수 효과였다. **도구의 비효율이 때로는 프로세스의 가드레일이 된다.**"

이 통찰은 일반화 가능하다 — IDE 통합 도구가 항상 좋은 게 아니라, **분석 목적에 따라 도구의
"제약"이 자원이 될 수 있다**는 메타 교훈.

## 오늘 고민한 문제 (What I struggled with)

### 고민 1: 프롬프트 원칙을 몇 가지로 할 것인가
**상황**:
처음에는 원칙을 10개까지 늘려야 할 것 같았다. "예외 처리도 명시", "주석 스타일 통일",
"네이밍 컨벤션 인용" 등.

**선택지**:
- A. 5가지 핵심 원칙만 — 외울 수 있는 분량, 실행 가능
- B. 10가지 상세 원칙 — 빠짐없음, 하지만 실행 어려움
- C. 3가지로 압축 — 너무 단순, 적용 모호

**결정과 이유**:
A 선택. **원칙은 외울 수 없으면 적용되지 않는다.**
10가지로 늘려놓으면 매 프롬프트마다 체크리스트를 다시 봐야 하는데, 그러면 결국 안 본다.
5가지는 머리에 담을 수 있고, 한 번 익숙해지면 무의식적으로 적용된다.

부족한 부분(주석, 네이밍 등)은 "검증 기준 동봉" 안에 흡수시켰다.
원칙 4를 잘 적용하면 그런 디테일이 자연스럽게 명시된다.

**의도적으로 적게 가는 것**이 데이터 모델에서 단일 엔티티를 선택한 것과 같은 원리다.
복잡함과 좋음을 혼동하지 않는 일관성.

### 고민 2: 안티 패턴 목록의 가치
**상황**:
안티 패턴 10가지를 정리하면서 "이거 너무 부정적인 문서 아닌가" 하는 생각이 들었다.
"잘 짠 프롬프트"의 예시만 보여주는 게 더 건설적이지 않을까.

**선택지**:
- A. 안티 패턴 빼고 좋은 예시만 — 긍정적 톤
- B. 안티 패턴 포함 — 회고에서 검증 가능
- C. 좋은 예시 + 안티 패턴 둘 다 — 분량 증가

**결정과 이유**:
B 선택. 결정적 근거는 **회고 시점의 검증 가능성**이다.

"좋은 예시"만 있으면 회고에서 "내가 좋은 예시처럼 했나?"를 물어야 하는데, 이건 주관적이다.
안티 패턴 목록이 있으면 "AP-3에 해당하는 프롬프트를 몇 번 썼나?"를 객관적으로 셀 수 있다.

이건 SRS의 Won't 처리(어제 배웠다)와 동일한 원리다. **무엇을 하지 말지를 명시하는 것이
무엇을 할지를 명시하는 것보다 측정 가능성이 높다.**
보고서 lessons learned에 "AP-1 발생 N회, AP-3 발생 M회" 같은 정량 데이터가 들어간다.

### 고민 3: `// TODO: 미이해` 마커를 진짜로 운영할 것인가
**상황**:
MNFR-02(100% 이해)를 강하게 잡고 있는데, 현실적으로 시간 부족 상황에서 일부 코드를
이해 못한 채 채택할 수 있다. 그때 `// TODO: 미이해` 마커를 단다는 규칙을 만들었지만,
이게 너무 가혹한 자기 검열 아닐까.

**선택지**:
- A. 마커 운영 — 정직, 하지만 자기 비판적
- B. 마커 빼고 "최선 다해 이해" 정도로 — 부드러움
- C. 마커는 두되 음수 평가가 아닌 학습 기록으로 정의 — 균형

**결정과 이유**:
C 선택. 마커를 운영하되, 이를 "실패 표시"가 아니라 "학습 큐"로 정의한다.

본 과제는 바이브코딩의 한계를 분석하는 게 목적이다.
**한계가 발현되지 않으면 분석할 게 없다.** 미이해 코드 0개를 만드는 게 목표가 아니라,
미이해 코드가 어떻게 발생하고 누적되는지를 추적하는 게 목적이다.

따라서 마커는 "내가 못났다"가 아니라 "여기 분석거리 발견"으로 본다.
회고에서 마커 수를 grep해서 카운트하는 행위 자체가 보고서의 정량 자료가 된다.

**평가 기준의 재설계**: 미이해 코드 = 본 과제의 데이터 포인트.
이 관점 전환이 오늘 일지의 핵심 교훈이다.

**오늘의 교훈 네 가지**:

첫째, **도구의 비효율이 때로는 프로세스의 가드레일이 된다.** Claude 웹의 수동 복사 절차는
"빠르지 않은" 특성인데, 본 과제 맥락에서는 그 비효율이 MNFR-02 운영의 가드레일로 작동한다.
도구를 평가할 때 "효율"만 보지 말고 "분석 목적과의 정합성"을 봐야 한다는 메타 통찰.
→ 보고서 3.4절(프롬프트 전략)에 인용. 도구 선정 결정 사례.

둘째, **원칙은 외울 수 없으면 적용되지 않는다.** 5가지 원칙으로 압축한 결정의 본질은
"실행 가능성 > 완벽성"이다. 10가지 원칙이 5가지보다 좋다는 직관은 틀렸다.
체크리스트의 항목 수가 늘어날수록 적용률은 떨어진다.
**프로세스 자체에도 단순함이 적용되어야 한다.**
→ 보고서 6.5절(종합 교훈)에 인용. 어제(Day 6) "복잡함과 좋음을 혼동하지 말 것"의 자기-적용 사례.

셋째, **안티 패턴 목록의 진짜 가치는 사후 분류에 있다.** 사전에 외워서 피하는 게 아니라,
회고에서 작성한 프롬프트를 분류하는 도구다. 이 관점 전환이 안티 패턴 목록을 "부담"에서
"분석 도구"로 바꾼다. SRS의 Won't 처리와 같은 원리다 — 무엇을 하지 말지 명시하는 것이
사후 측정을 가능하게 만든다.
→ 보고서 6.3절(구현 단계의 교훈)에 인용. "프롬프트 회고 방법론" 사례.

넷째, **본 과제의 목적은 한계 제거가 아니라 한계 분석이다.** `// TODO: 미이해` 마커 운영을
"실패 표시"가 아니라 "학습 큐"로 재정의한 결정이 본 교훈의 핵심이다.
바이브코딩의 한계를 0으로 만드는 게 목표라면, 한계가 발현되지 않아 분석할 자료가 없다.
**한계가 발현되는 것이 본 과제의 데이터 포인트다.** 이 관점은 모든 회고에 적용된다.
→ 보고서 1.3절(가설)에 인용. 가설을 검증하는 데이터의 정의.

## 설계 단계 7일 회고 (조기 회고)

원래 회고는 이터레이션 종료 시점에 한다. 하지만 설계 단계 종료를 표시할 가치가 있어
이 절에 간단히 정리한다.

### Keep (계속할 것)
- 매일 일지 작성 — 7일간 1일도 빠짐없이 작성됨
- 결정마다 근거를 표로 정리 — 보고서 인용성이 높음
- "의도적으로 배제한 것" 명시 습관 — Won't, 미포함 필드, 안티 패턴 등 일관되게 적용됨
- AI 토의 발췌를 일지에 보존 — 토의가 결정에 어떻게 영향을 줬는지 추적 가능

### Problem (문제가 된 것)
- 처음 며칠은 일정 추적이 흔들림 (Day 2~3 합쳐서 작업한 적 있음) — 정상화됨
- ADR을 표준 양식으로 처음 작성할 때 시간 초과 (Day 4) — 이후 익숙해짐
- 일부 일지의 분량이 과도 — 일지의 목적은 토의 보존이지 보고서 초안이 아님

### Try (이터레이션 1에서 시도할 것)
- 프롬프트 작성 시간 1분 단위 측정 (지금까지 안 함)
- 매일 마지막 5분을 "최종 보고서 골격에 메모 추가"에 사용 (Day 19~20 부담 분산)
- 미이해 마커가 발생하면 그 날 일지에 명시적으로 기록
- **본 채팅 세션을 그대로 이어가기** (LLM 선정 결정의 운영 규칙)
