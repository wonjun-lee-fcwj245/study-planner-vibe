## 오늘 고민한 문제 (What I struggled with)

### 고민 1: 와이어프레임을 손으로 그릴까, 디지털로 만들까
**상황**:
"와이어프레임" 하면 보통 종이에 손으로 그리는 이미지가 떠오른다.
하지만 텍스트 기반 ASCII + 별도 시각화로 가는 게 더 나을 수도 있다.

**선택지**:
- A. 손 스케치 → 사진 찍어 임베드 — 전통적, 빠름
- B. Figma/Excalidraw로 디지털 와이어프레임 — 깔끔, 도구 학습 비용
- C. 마크다운 + ASCII로 영역만 명시 + SVG로 시각화 — 버전 관리 친화

**결정과 이유**:
C 선택. 결정적 이유는 **버전 관리 친화성**이다. 손 스케치 사진은 git에 들어가도 diff가 안 보이지만,
마크다운/ASCII는 줄 단위 추적이 가능하다. Day 6~7에 와이어프레임이 수정될 때 변경 흔적이 남는다.
또한 보고서에 인용할 때도 마크다운에서 바로 복사 가능하다.

단점은 시각적 충실도가 낮다는 점인데, 이건 와이어프레임의 목적과 부합한다.
**와이어프레임은 시각적 디테일이 아니라 정보 구조를 설계하는 도구**이므로, 오히려 단순한 표현이 적합하다.

### 고민 2: 통계 화면을 별도 화면으로 둘지, 메인 보드 안에 통합할지
**상황**:
화면이 2개면 라우팅 또는 화면 전환 로직이 필요하다. 1개 화면 안에 다 넣으면 단순하지만 정보 과잉이 우려된다.

**선택지**:
- A. 별도 화면 + 라우터 — React Router 같은 도구 필요해짐
- B. 별도 화면 + 단순 영역 전환 (display: none/block) — 라우터 없이 가능
- C. 한 화면에 모두 통합 — 정보 과잉, 첫인상 부담
- D. 메인 보드 푸터에 미니 차트만 — 통계 기능 축소

**결정과 이유**:
B 선택. 두 화면을 유지하되 라우터 없이 단순한 영역 토글로 처리한다.
- A는 ADR-002(프레임워크 없음) 결정과 충돌
- C는 페르소나 1의 "30초 이내 확인" 요구와 충돌 (첫 화면이 복잡해짐)
- D는 페르소나 2의 "주간 진도 시각 확인" 요구를 만족시키기 어려움

B는 ADR-002의 단순성을 유지하면서 두 화면의 목적을 분리할 수 있다.
**프로세스 적용의 효과 사례**: ADR-002가 와이어프레임 단계에서 이미 의사결정에 영향을 주고 있다는 점.
설계 결정이 후속 결정의 제약 조건으로 작용하면서 일관성이 자동으로 유지된다.

### 고민 3: "의도적으로 배제한 UI 요소"를 와이어프레임 문서에 적을지
**상황**:
SRS에는 "Won't 처리 사유"가 있다. 와이어프레임에도 비슷한 항목을 두는 게 중복 같다.

**선택지**:
- A. 와이어프레임 문서에는 적지 않음 — SRS에 이미 있음
- B. 와이어프레임 관점에서 별도로 적음 — UI 요소 중심으로 재서술
- C. SRS 항목을 그대로 복사 — 일관성 강조

**결정과 이유**:
B 선택. SRS의 Won't는 **기능 단위**고, 와이어프레임의 배제는 **UI 요소 단위**다.
예를 들어 "사이드바 없음"은 어떤 FR의 Won't도 아니지만 화면 구성 결정으로서 명문화할 가치가 있다.
**같은 결정이라도 어느 산출물에 어떻게 표현되느냐가 다르다**.

##  신규 기능 요구에 대한 의사결정 — "자동 분배" 거절

### 발단

Day 5 작업 막바지에 새 기능 아이디어가 떠올랐다.

> "일주일 고정 일정(수업, 알바 등)을 입력받고, 일주일치 공부할 항목들을 입력하면
> 시스템이 알아서 빈 시간에 학습 항목을 분배해주는 기능"

직관적으로 매우 매력적이었다. 페르소나 1(이원준)의 사용 맥락에도 잘 맞아 보였다 — 6과목을
관리하는 학기 중 학생에게 "자동으로 일정에 끼워 넣어주는 도구"는 유용하다.

기술적으로도 충분히 가능했다. Greedy 알고리즘으로 빈 시간 블록을 추출하고 학습 항목을
큰 것부터 배치하는 방식이면 100~150줄 정도의 JS로 구현 가능하다고 판단했다.

**이 시점이 본 과제에서 처음으로 "범위 확장 유혹"이 발생한 순간이다.**

### 거절 결정의 근거

즉흥적으로 수용하지 않고 SRS·비전 문서로 돌아가 검토한 결과, 다음 네 가지 충돌이 발견됐다.

#### 근거 1: 비전 문서의 Out of Scope 명시
비전 문서 6장 Out of Scope 항목에 **"AI 기반 학습 추천"** 이 명시되어 있다.
자동 분배는 "AI 기반 추천"의 한 형태로 해석된다. 알고리즘이 단순(Greedy)하다고
해서 본질이 달라지지는 않는다 — 시스템이 사용자 대신 학습 일정을 결정하는 행위 그 자체가
배제된 범주에 속한다.

#### 근거 2: 비전 문서의 핵심 가치 "단순함"
비전 4장의 핵심 가치 세 가지 중 두 번째가 **"단순함: 학습 관리에 꼭 필요한 기능만 — 추가, 완료, 통계 3가지"** 이다.
자동 분배는 4번째 축을 추가하는 것이며, 이는 "꼭 필요한 기능만"의 정의에서 벗어난다.

#### 근거 3: MoSCoW 분류 체계 외부
어제 확정한 MoSCoW 분류(FR-01~13)에서 어떤 카테고리에도 들어가지 않는 완전히 새로운 기능이다.
받아들이려면:
- SRS 버전을 0.4로 올리고 새 UC-06 추가
- 새 FR-14, FR-15 도출
- 기존 13개 FR과의 우선순위 재검토
- 와이어프레임에 일정 입력 화면 추가
- 이터레이션 작업량 재추정

총 1~2일의 재설계 작업이 발생한다. 남은 시간 안에서 이것은 현실적이지 않다.

#### 근거 4: 페르소나 일관성 검토
페르소나 1(이원준)의 목표를 다시 읽어보면:
> "다양한 프로젝트를 진행하면서 필요한 여러 학습 내용을 **체계적으로 관리**"

이 "체계적 관리"의 주체는 **사용자 본인**이다. 자동 분배는 그 주체를 시스템으로 이전한다.
페르소나 2(박지훈)도 마찬가지로 "스스로 페이스 조정"이 사용 맥락이다.
두 페르소나 모두 자동 분배가 필요한 페르소나가 아니다. 만약 자동 분배 기능이 진짜로 필요하다면
새 페르소나(예: "시간 계획에 약한 학생")가 추가되어야 하는데, 본 버전은 그런 페르소나를
의도적으로 배제했다 (SRS 페르소나 배제 목록).

### 거절을 통해 확인된 프로세스의 효과

이 의사결정이 본 과제의 lessons learned에서 가장 강력한 사례가 될 가능성이 있다.

**프로세스 문서가 없었다면 무슨 일이 일어났을까?**
- 즉시 LLM에게 "주간 자동 분배 기능을 추가해줘"라고 프롬프트를 던졌을 것이다.
- LLM은 친절하게 100~200줄 코드를 생성했을 것이다.
- 기존 학습 항목 데이터 구조와 결합도가 높은 코드가 됐을 것이다.
- 후반에 통계 기능을 만들 때 데이터 구조 충돌이 발생했을 가능성이 높다.
- 결과적으로 어느 기능도 완성도 있게 마무리되지 않았을 것이다.

**프로세스 문서가 있었기에 일어난 일**
- 거절의 근거를 즉석에서 만들지 않고 기존 문서에서 추출했다.
- 거절의 과정에서 비전 문서·SRS·페르소나의 일관성이 다시 한 번 검증됐다.
- 거절 사유 자체가 보고서의 사례 연구가 됐다.
- 향후 비슷한 유혹이 와도 같은 절차로 빠르게 판단할 수 있게 됐다.

**보고서 인용 메모**:
> "Day 5에 '주간 자동 분배' 기능 추가에 대한 자기-유혹이 발생했다.
> SRS의 비전·MoSCoW·페르소나 세 층의 검토를 거쳐 거절했다.
> 흥미롭게도 거절에 소요된 시간은 약 10분이었다. 이는 Day 1~4에 SRS 작성에 투자한
> 약 4시간이 만든 효과다. **요구사항 분석 단계의 비용은 단순히 '기능을 정의하는 시간'이 아니라
> '미래에 추가될 잘못된 기능을 차단하는 시간'에 대한 선불 결제다.**"

### Future Work로 흔적 보존

거절이 "없었던 일"이 되지 않도록, 별도 문서로 보존했다.

## 오늘의 작은 lessons learned

- [x] 프롬프트 품질과 산출물 품질의 관계
- [x] 프로세스 단계를 건너뛰고 싶은 유혹과 그 결과
- [ ] AI 코드를 이해하지 못한 채 쌓일 때의 리스크 (아직 코딩 전)
- [ ] 회고가 다음 사이클에 미친 영향

**오늘의 교훈 세 가지**:

첫째, **와이어프레임의 가치는 "그려진 것"이 아니라 "그리는 과정"에 있다.** 영역을 나누고 각 영역에
FR/UC를 매핑하면서, SRS만 봤을 때는 안 보이던 누락이 보였다. 예를 들어 "오늘 진도 카드"가 헤더에
들어가야 한다는 결정은 SRS의 FR-08(진도율 표시)을 화면에 어디 둘지 고민하면서 나왔다.
**산출물이 다음 산출물의 모자란 점을 드러내는 게 프로세스의 가치다.**
→ 보고서 6.2절(설계 단계의 교훈)에 인용.

둘째, **ADR이 후속 결정의 제약 조건이 된다.** 통계 화면을 별도 화면으로 둘지 통합할지 고민할 때,
ADR-002(프레임워크 없음)가 자동으로 "라우터 도입 옵션 A"를 배제했다. 결정의 일관성이 의식적인
노력 없이 유지된 사례다.
→ 보고서 6.5절(종합 교훈) "프로세스 적용의 비용 vs 편익"에 인용.

셋째, **요구사항 분석 단계의 비용은 미래 결정에 대한 선불 결제다.** "자동 분배" 기능을 거절하는 데
약 10분이 걸렸는데, 그 10분이 가능했던 이유는 Day 1~4에 SRS·비전·페르소나를 4시간 들여 만들어둔
덕분이다. 이 문서들이 없었다면 거절의 근거를 즉석에서 만들거나, 충동적으로 수용했을 것이다.
**프로세스 문서의 진짜 가치는 그것이 정의하는 것이 아니라 그것이 차단하는 것에서 나온다.**
→ 보고서 6.1절(요구사항 분석 단계의 교훈) **결정적 사례**로 인용. 바이브코딩의 한계
