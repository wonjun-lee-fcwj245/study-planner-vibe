## 오늘 고민한 문제 (What I struggled with)

### 고민 1: 프로세스 모델 선택 — 폭포수 vs 반복적
**상황**:
과제가 "프로세스 적용"을 요구하므로 폭포수 모델이 단계 구분이 명확해 평가자에게 보여주기 쉬워 보였다.
하지만 바이브코딩의 본질은 LLM과의 빠른 대화 사이클이라, 폭포수와는 맞지 않는다고 판단했다.

**선택지**:
- A. 폭포수 — 단계 명확, 문서 강제. 하지만 바이브코딩과 부정합.
- B. 반복적 — 회고를 통한 점진적 개선. 바이브코딩과 정합. 단, 1인 20시간에 3회 반복이 빡빡할 위험.
- C. 애자일/Scrum — 적응성 좋음. 단, 1인 프로젝트에 의례(daily standup 등)가 과함.

**결정과 이유**:
B. 반복적 모델을 채택했다. 이유는 세 가지.
첫째, 바이브코딩과 반복적 모델은 모두 "짧은 사이클의 반복"이라는 공통 DNA가 있어 자연스럽다.
둘째, 매 이터레이션의 KPT 회고가 그 자체로 보고서 lessons learned의 1차 자료가 된다.
셋째, MVP를 일찍 확보하면 후반에 문제가 생겨도 최소 버전은 제출 가능하다 (위험 분산).

### 고민 2: 프로젝트 형태 — 순수 웹 vs React
**상황**:
React를 쓰면 더 "제대로 된 프로젝트"처럼 보일 수 있다는 유혹이 있었다.

**선택지**:
- A. 순수 HTML/CSS/JS — 환경 설정 0분, 즉시 시작 가능.
- B. React — 모던하지만 Node·npm·Vite 설정에 첫날이 통째로 날아갈 수 있음.

**결정과 이유**:
A. 순수 웹을 선택. 본 과제의 진짜 평가 대상은 "프로세스 적용 경험"이라 생각했다.
환경 설정 시간을 아껴서 요구사항 분석과 회고에 시간을 더 쓰는 게 점수에 직접적이다.
또한 GitHub Pages로 즉시 배포되어 평가자가 데모를 바로 볼 수 있다는 장점도 있다.

## AI/팀원과의 토의 발췌

오늘은 Claude와 프로젝트 계획 전반에 대해 토의했다. 주요 흐름:

```
나: 바이브코딩으로 학습 플래너를 만들 예정이야. 계획부터 작성해줘.

Claude: 단순히 학습 플래너를 만드는 것이 아니라, "프로세스에 입각한 바이브코딩"의
효과를 검증하는 메타 프로젝트로 봐야 한다고 지적. 산출물(학습 플래너)은
실험 대상이고, 진짜 산출물은 분석 보고서임을 명확히 함.

→ 이 지적이 핵심이었다. 학습 플래너의 기능에만 집중했다면 "지속적 토의 증빙"
   같은 평가 기준을 놓쳤을 것이다.

나: 다음에 뭘 먼저 해야 해?

Claude: SRS 작성보다 repo 구조와 문서 템플릿 먼저 만드는 것을 권장.
이유는 (a) 첫 커밋이 큰 문서 하나로 시작되면 "지속적 진행" 평가에 불리하고,
(b) repo 구조가 먼저 잡혀야 후속 산출물의 위치가 명확하기 때문.

→ 동의. 
```
