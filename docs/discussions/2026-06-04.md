## 오늘의 가장 중요한 발견: Phase 4 가설 수정

어제 Phase 4 후보로 제시한 가설이 오늘 검증을 거쳐 정밀화됐다.

### 어제의 가설 (Day 16)
> "LLM은 모호한 요구를 만나면 **암묵적 일관 원칙**으로 채운다.
>  세 가지 모호한 결정 모두 '데이터 손실 방지' 원칙으로 일관."

### 오늘 검증 결과
의도적 모호함 1개를 추가 도입: "코드 중복이 발견되면 통합할지 분리 유지할지 LLM 판단."
LLM의 결정: 부분 통합 + 부분 분리.
LLM 명시 근거: **"각 함수 책임 명확, 변경 영향 범위 최소화."**

이는 어제의 "데이터 손실 방지" 원칙**과 다른** 원칙.

### 정밀화된 가설 (Day 17)
> "LLM은 모호함을 채울 때 **맥락에 맞는 원칙**을 선택한다.
>  사용자 데이터 맥락에서는 '데이터 손실 방지'.
>  코드 구조 맥락에서는 '변경 영향 범위 최소화'.
>  각 맥락에 적절한 원칙이 자동 선택된다 — 단일 절대 원칙이 아니라 맥락 의존적 원칙."

### 이게 본 과제 학술적 가치

가설이 5번 진화함:

```

Phase 4 정밀화 (Day 17): "맥락에 맞는 원칙을 선택한다"        [최종]
```

**가설 자체가 점진적 검증을 거치면서 정밀해진다** — 본 과제의 메타 메시지.

## 오늘 고민한 문제 (What I struggled with)

### 고민 1: NFR 3개를 한 프롬프트로 묶을지 (원칙 3 위배 문제)
**상황**:
프롬프트 전략 원칙 3 "단일 책임" — 한 프롬프트에 한 기능만. 그런데 NFR-04, 05, 07이 결합도 매우 높음.

**선택지**:
- A. 원칙 준수 — 3개 프롬프트로 분리, 시간 3배
- B. 의식적 위배 — 1개 프롬프트, 합리적 근거 명시
- C. 두 개로 묶기 (NFR-04+07 / NFR-05) — 절충

**결정과 이유**:
B 선택. 결정적 근거:
(1) 세 NFR이 같은 코드(함수, 주석, 키보드 처리)를 다룸 — 분리하면 같은 코드를 3번 검토.
(2) 회귀 위험을 한 번에 검증 가능 — 분리하면 검증도 3번.
(3) 원칙은 **합리적 기본값**이지 절대 규칙이 아님 — 더 좋은 이유가 있으면 의식적 위배 가능.

**핵심 통찰**: 원칙의 의식적 위배는 **안티 패턴이 아니라 원칙의 성숙한 적용**이다.
원칙을 외워서 그대로 따르는 것보다, 원칙의 의도를 이해하고 맥락에 맞게 적용하는 게 더 어렵고 가치 있음.
→ 보고서 6.3절(구현 단계) "프롬프트 원칙의 합리적 위배" 사례.

### 고민 2: Phase 4 가설을 단일 원칙으로 둘지, 수정할지
**상황**:
어제 가설이 "데이터 손실 방지 = 단일 원칙"이었는데, 오늘 다른 원칙 발현.
원래 가설을 고집할지, 수정할지.

**선택지**:
- A. 어제 가설 고집 (오늘 사례를 예외로 해석) — 일관성, 그러나 부정확
- B. 가설 정밀화 (단일 → 맥락별) — 정확성, 가설 진화
- C. 가설 폐기 + 새로 쓰기 — 과한 변경

**결정과 이유**:
B 선택. 가설 수정은 가설 폐기가 아니라 **정밀화**다.
어제 가설의 "일관 원칙" 부분은 유지 — 오늘 사례도 일관 원칙(영향 범위 최소화)으로 결정됨.
다만 "단일 원칙"이 부정확 — 맥락별로 다름.

**핵심 통찰**: 보고서에서 "처음 세운 가설이 맞았다"보다 "가설이 어떻게 진화했는가"가 훨씬 강력하다.
**가설의 진화 자체가 본 과제의 학술적 가치다.**
→ 보고서 1.3절, 7.1절 핵심 메시지.

### 고민 3: NFR-05 브라우저 호환성 테스트를 본인이 할지, 명세만 둘지
**상황**:
LLM은 호환성 명세는 만들 수 있지만 실제 Chrome/Firefox/Edge 테스트는 못 함.

**선택지**:
- A. 본인이 3개 브라우저 모두 직접 테스트 — 시간 30분 추가
- B. Chrome만 테스트, 다른 브라우저는 호환성 명세로 추정 — 시간 절약
- C. 명세만 두고 v1.0 출시, 실제 테스트는 v1.1로 미룸 — 본 과제 범위 밖

**결정과 이유**:
B 선택. **본 과제의 범위 안에서 합리적 절충.**
NFR-05는 본 과제 메인 분석 대상이 아님 — 본 과제는 "프로세스 적용 분석"이지 "브라우저 호환성"이 아님.
명세에 "Chrome 90+, Firefox 88+, Edge 90+"를 명시했고, 사용 API들(crypto.randomUUID, Set 등)이
대상 브라우저 안정판에서 지원됨을 확인한 것으로 충분.

이는 **본 과제의 범위 명확성**을 보여주는 사례 — Day 5의 자동 분배 거절, FWC-001과 같은 결.
**과제의 핵심에 집중하고, 부수적 부분은 합리적 기본값으로 처리.**
→ 보고서 6.5절(종합 교훈) "과제 범위의 명확성 유지" 사례.

**오늘의 교훈 다섯 가지**:

첫째, **Phase 4 가설 정밀화 — 단일 원칙에서 맥락별 원칙으로.**
어제 가설("LLM은 단일 일관 원칙으로 모호함을 채운다")이 오늘 검증을 거쳐 정밀화됨.
LLM은 사용자 데이터 맥락에선 "데이터 손실 방지", 코드 구조 맥락에선 "영향 범위 최소화" 원칙 적용.
**가설의 진화 자체가 본 과제의 학술적 가치다.**
→ 보고서 1.3절, 5.2절, 7.1절 핵심 인용. 가설 진화 5 Phase 다이어그램 필요.

둘째, **원칙의 의식적 위배는 안티 패턴이 아니라 성숙한 적용이다.**
NFR-04, 05, 07을 한 프롬프트로 묶음 — 원칙 3(단일 책임) 위배처럼 보이지만,
결합도 분석에 기반한 의식적 결정. AP-4("FR-01, FR-02, FR-03 다 해줘")와의 차이는 **분석의 유무**.
→ 보고서 6.3절(구현 단계) "프롬프트 원칙의 의식적 위배 vs 안티 패턴" 사례.

셋째, **자발 추가는 새로움이 있어야 발생 — 리팩토링에서는 감소 (가설 강화).**
오늘 자발 추가 2건 (vs 어제 4건). Day 15 FR-10(패턴 재사용, 0건)과 일관.
**"자발 추가의 발생 조건 = 새로움 + 보통 난이도"** 가설이 3번째 데이터로 강화됨.
→ 보고서 6.3절 "LLM 자발 추가의 발생 조건" 정량 증거.

넷째, **NFR-05 같은 자동화 불가 검증은 본인 책임으로 명시 분리.**
LLM이 호환성 명세는 만들지만 실제 Chrome/Firefox/Edge 테스트는 본인 별도 수행.
**자동화 불가능한 검증은 명시적으로 사용자 책임으로 분리** — 본 과제의 책임 한계 명시.
→ 보고서 6.4절(품질 관리) "LLM의 책임 한계 명시" 사례.

다섯째, **NFR-07 (주석 100%) 달성으로 본 과제 메타 NFR 4개 중 4개 모두 검증 통과.**
이로써 본 과제의 메타 NFR 측면이 완전히 통과됨. 내일은 코드 검증보다 회고와 메타 분석에 집중 가능.
