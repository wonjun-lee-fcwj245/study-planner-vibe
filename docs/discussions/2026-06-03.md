## 오늘의 가장 중요한 발견: LLM의 암묵적 일관 원칙

오늘은 의도적으로 검증 기준 7개 중 3개를 **명시 안 함**으로 했다 (T3 강도 증가 적용).
LLM이 세 가지 모두 동일한 암묵적 원칙으로 결정:

| 모호한 상황 | LLM 결정 | 명시 근거 |
|----------|---------|---------|
| 빈 제목 저장 | 원래 값 유지 | 데이터 무결성 |
| 다른 항목 클릭 | 현재 저장 후 이동 | 작업 손실 방지 |
| 수정 중 체크박스 | 토글 무시 | 사용자 의도 충돌 보호 |

**핵심 관찰**: 세 결정 모두 "**데이터 손실 방지**"라는 일관 원칙.
LLM은 명시되지 않은 결정에서 **암묵적 일관 원칙**을 적용한다.

### 본 발견이 가설에 미치는 영향

가설 Phase 4 후보:
> "LLM은 명시되지 않은 의사결정을 만나면 암묵적 일관 원칙으로 채운다.
>  그 원칙이 사용자 가치와 정합하면 자발 결정이 안전한 채택 후보가 된다."

이는 자발 추가 가설의 확장:
- 자발 **추가**: 명시 안 한 기능을 LLM이 추가
- 자발 **결정**: 명시 안 한 의사결정을 LLM이 선택

두 가지가 동일한 메커니즘(암묵적 일관 원칙)으로 작동할 가능성.

→ 보고서 6.3절(구현 단계 교훈) 신설 절: "LLM 모호함 처리의 암묵적 원칙."
→ 보고서 1.3절(가설) Phase 4 후보로 명시.

## 오늘 고민한 문제 (What I struggled with)

### 고민 1: 의도적 모호함이 실패하면 어떡할지
**상황**:
T3(의도적 어려움 강도 증가)에 따라 검증 기준 3개를 모호하게 두기로 결정. 그런데 LLM이 합리적이지 못한 결정을 하면?
예: 빈 제목을 그대로 저장해서 데이터 손실 발생.

**선택지**:
- A. 모호함 그대로 두기 — 진짜 실험
- B. 안전 가드(어차피 빈 제목은 거절) 추가 명시 — 안전
- C. 모호함 명시 + 추가로 "합리적 기본값을 자발 선택할 것" 메타 지시

**결정과 이유**:
A 선택. 본 과제는 분석이 목적이지 결과 보장이 목적이 아니다.
만약 LLM이 데이터 손실하는 결정을 했다면, **그것 자체가 본 과제 보고서의 가장 강력한 경고 사례**가 된다.

결과적으로 LLM은 안전한 결정을 했지만, 만약 안 그랬다면 더 풍부한 분석 자료가 됐을 것이다.
**의도적 실험 설계의 가치는 결과 무관 — 양쪽 다 데이터.**
→ 보고서 6.4절(품질 관리) "의도적 실험의 설계 원칙" 사례.

### 고민 2: 응답에 "LLM 결정 설명" 요청 — AP-9에 가깝지 않나
**상황**:
프롬프트 마지막 줄에 "의도적 모호한 검증 기준에 대해 LLM이 어떻게 선택했는지 별도 설명"을 요청.
이건 코드 외에 메타 설명을 요청하는 것 — 안티 패턴 AP-9("코드만 줘, 설명 빼고")의 반대?

**선택지**:
- A. 메타 설명 요청 — 분석 자료 풍부, 그러나 응답 길어짐
- B. 코드만 요청 후 본인이 결정 추론 — 깔끔, 그러나 추론 오류 가능
- C. 일부만 메타 설명 — 균형

**결정과 이유**:
A 선택. AP-9는 "이해 없이 채택" 위험에 대한 것인데, 메타 설명 요청은 정반대 — 이해를 강화하는 요청.
**원칙은 도구이지 절대 명령이 아니다.** 본 과제 분석 목적에 따라 도구를 응용 적용.

LLM이 자기 결정을 명시한 덕에 본 일지의 "고민/결정/근거" 분석이 가능. 보고서 분석 자료의 깊이가 1단계 추가.
→ 보고서 6.3절 "프롬프트의 메타 요청" 사례.

### 고민 3: SRS의 부정확성을 또 발견 — 어떻게 처리할지
**상황**:
SRS 재독 중 FR-11에 대응되는 UC가 없음을 발견. 이터2 회고의 FR-05 사례에 이어 두 번째.

**선택지**:
- A. UC-06 (제목 수정) 신규 추가, SRS 0.3.2로 업그레이드
- B. SRS 변경 이력에만 한 줄 (이터2 FR-05 처리와 동일)
- C. 이터3 회고 P 항목으로만 기록

**결정과 이유**:
B 선택. 이터2 FR-05와 동일 처리 방식 — 일관성.
다만 이터3 회고 P 항목에 "**SRS 부정확성 누적**" 사례 추가 예정.

**핵심 통찰**: 두 번의 SRS 부정확성 발견(FR-05, FR-11 UC 누락)이 누적되면서 한 가지 패턴이 보임 —
**"SRS는 한 번에 완성되지 않는다. 구현하면서 부정확성이 드러난다."**
→ 보고서 6.4절(품질 관리) "요구사항 문서의 점진적 정확성" 사례. 이터1 회고 한계 분석의 확장.

        만약 다른 원칙(예: 코드 단순성)이 적용되면 가설이 부분 수정된다.
        어느 쪽이든 보고서 분석 거리.

나: SRS의 부정확성을 두 번이나 발견했어. SRS 작성을 더 잘 했어야 한 거 아냐?

Claude: 두 가지 관점:
        (1) SRS를 완벽하게 작성하기는 불가능. 구현해보지 않은 시점에 모든 UC를 다 잡을 수 없음.

→ 적용: 보고서 6.4절 "요구사항 문서의 점진적 정확성" 사례로 인용.
   "완벽한 SRS"가 아니라 "추적 가능한 SRS"가 본 과제 가치.

첫째, **LLM은 모호함을 일관된 암묵적 원칙으로 채운다 (가설 Phase 4 후보).**
세 모호한 결정 모두 "데이터 손실 방지" 원칙으로 일관. 자발 추가 가설의 확장 —
"자발 결정"도 동일 메커니즘으로 작동할 가능성.
**Day 17에서 추가 검증 예정. 가설이 확증되면 본 과제의 학술적 핵심 메시지에 Phase 4 추가.**
→ 보고서 1.3절, 6.3절 핵심 사례 후보.

둘째, **의도적 실험의 가치는 결과와 무관하다.** T3 강도 증가는 "한계 재발현"이 목표였으나,
실제로는 한계 발현 대신 새 분석 차원(암묵적 원칙)이 열렸다. 실험은 가설이 맞아도 데이터, 틀려도 데이터다.
**프로세스에 입각한 실험 설계가 보고서 분석의 깊이를 결정한다.**
→ 보고서 6.4절(품질 관리) "의도적 실험의 설계 원칙" 사례.

셋째, **SRS는 한 번에 완성되지 않는다 — 구현이 SRS를 보강한다.**
SRS 부정확성 2건(FR-05 위치, FR-11 UC 누락) 누적. 이는 실패가 아니라 SRS의 본질 — 구현 전에 모든
시나리오를 잡을 수 없음. **SRS의 가치는 "완벽함"이 아니라 "추적 가능성"에 있다.**
→ 보고서 6.4절 "요구사항 문서의 점진적 정확성" 사례.

넷째, **자발 추가 4개 카테고리가 동시 발현 — 분류의 완성도 신호.**
오늘 4건 자발 추가가 NFR 정합, UX 개선, 엣지 처리, 디자인 일관성에 정확히 1건씩.
