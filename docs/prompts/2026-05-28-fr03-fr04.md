## 교훈 (이 프롬프트 경험에서 배운 것)

### 1. 첫 시도 채택률 100%가 드디어 깨졌다 — 그리고 그게 좋은 일이다
FR-01, 02, 03은 모두 첫 시도 채택이었으나 FR-04는 2회 걸렸다.
**이것이 본 과제의 가장 중요한 데이터 포인트일 수 있다.**

이유: 쉬운 작업(CRUD)에서는 프로세스 적용의 효과가 잘 안 드러난다. LLM이 워낙 잘하니까.
어려운 작업(엣지 케이스가 많은 영속성)에서야 비로소 차이가 보인다.

핵심 관찰: **시도 1의 누락(시크릿 모드 getItem, 필드 검증)은 검증 기준에 명시했는데도 빠졌다.**
이건 LLM이 "기본 경로"를 우선하고 "예외 경로"를 누락하는 경향을 보여준다.
바이브코딩의 한계: **엣지 케이스는 명시해도 누락될 수 있다.**

그런데 프로세스가 이 한계를 어떻게 완화했는가?
- 검증 기준을 명시해뒀기 때문에, 시도 1의 누락을 **즉시 발견**할 수 있었다.
- 검증 기준이 없었다면 "동작하는 것 같은 코드"를 채택하고, 나중에 시크릿 모드 사용자가
  버그를 만났을 것이다.
→ 보고서 6.3절(구현 단계의 교훈) **결정적 사례**. "프로세스는 LLM의 누락을 막지 못하지만,
   누락을 즉시 발견하게 만든다."

### 2. 시도 2의 프롬프트가 핵심 기술이다
시도 2에서 "방금 빠진 두 가지"를 구체적으로 짚었다. "다시 해줘"(안티 패턴 AP-2)가 아니라
"이 두 가지만 추가하고 나머지는 유지"라고 명시했다.
결과: 시도 2가 정확히 그 두 가지만 고치고 나머지를 보존했다.

만약 "localStorage 제대로 다시 해줘"(AP-2)라고 했다면, LLM이 전체를 다시 써서
시도 1의 정상 부분까지 바뀌었을 것이고, 본인이 또 전체를 검토해야 했을 것이다.
→ 보고서 6.3절 "디버깅 프롬프트의 기술" 사례.

### 3. 자발 추가 패턴 — 이번엔 발생 안 함
Day 8(escapeHtml), Day 9(transition)에 이어 자발 추가를 기대했으나, FR-04에서는 없었다.
오히려 명시한 것도 누락했다. **가설 수정**: LLM의 자발 추가는 "쉬운 작업"에서 주로 발생하고,
"어려운 작업"에서는 기본 요구 충족에 집중하느라 자발 추가가 줄어든다.
→ 자발 추가 패턴 분석이 더 풍부해졌다. 보고서 6.3절 추가 데이터.

### 4. 안티 패턴 발생: 0건
시도 2에서 AP-2("전체 다시 써줘")를 의식적으로 피한 게 핵심.

### 5. 가설 검증의 전환점
Day 8~9는 "프로세스가 있으면 다 잘 된다"처럼 보였다. FR-04는 그 단순한 그림을 복잡하게 만들었다.
**진짜 결론**: 프로세스는 바이브코딩을 완벽하게 만들지 않는다.
프로세스는 (a) 한계를 즉시 발견하게 하고, (b) 수정을 정밀하게 만든다.
이 두 가지가 "완벽한 코드"보다 더 중요하고 현실적인 효과다.
→ 보고서 1.3절(가설)과 7.1절(가설 검증 결과)의 핵심 메시지.
