## 교훈 (이 프롬프트 경험에서 배운 것)

### 1. 사전 설계가 프롬프트 길이의 90%를 차지했다
프롬프트의 본문은 [요청] 5줄밖에 안 된다. 나머지 35줄은 [맥락]·[제약]·[검증 기준]·[출력 형식]이고,
이 모두가 Day 1~7의 설계 문서에서 그대로 인용된 것이다. **프롬프트 자체를 짜는 시간(8분)보다
설계 문서를 인용하는 흐름이 압도적으로 많았다.** 이게 "프로세스에 입각한 바이브코딩"의 실제 모습이다.

### 2. LLM이 자발적으로 추가한 escapeHtml이 흥미롭다
프롬프트에서 XSS 방어를 요청하지 않았는데도 LLM이 자발적으로 escapeHtml을 추가했다.
이는 양면적이다.
- **긍정**: 보안 의식이 있는 코드. 본인이 빠뜨릴 수 있는 부분을 LLM이 채워줌.
- **부정**: 프롬프트에 없는 기능이 추가됨 — 다른 상황에서는 범위 부풀림의 시작점일 수 있음.
이번에는 긍정 사례지만, 회고에서 "LLM이 자발적으로 추가한 코드"를 추적할 가치가 있다.

### 3. 첫 시도에 채택된 사례의 분석
첫 시도에 모든 검증 기준을 통과한 이유를 분석하면:
- 프롬프트가 매우 구체적이었다 (검증 기준 5개를 명시적으로 적었다)
- 데이터 모델·ADR을 인용해서 LLM이 "맞춰서" 만들 여지를 제거했다
- 단일 책임 원칙 준수 — FR-01만 요청했다 (FR-02, FR-03을 묶지 않았다)
**프롬프트 원칙 5가지 중 4개(맥락·FR ID 인용·단일 책임·검증 동봉)가 모두 작동한 결과.**
이건 보고서 6.3절(구현 단계의 교훈) "잘 만든 프롬프트의 특징"에 직접 인용 가능.

### 4. 안티 패턴 발생: 0개
회고용 분류: AP-1~AP-10 어느 항목에도 해당되지 않음.
프롬프트 전략 10절의 평가 기준 중 "안티 패턴 발생 횟수" 지표에 0건 기록.

### 5. 본 시도가 본 과제의 가설을 부분적으로 입증한다
가설: "프로세스에 입각한 바이브코딩은 한계를 완화한다."
오늘 데이터:
- FR ID 인용률 100% (목표 100% 달성)
- 첫 시도 채택률 100% (목표 60%를 크게 상회)
- 미이해 코드 0건 (목표 5건 이하 달성)

다만 첫 사례 하나로 가설을 단정할 수 없다. FR-02~04에서도 같은 결과가 재현되는지가 진짜 검증이다.
이터레이션 1 회고(Day 11)에서 4개 FR의 데이터를 종합한 뒤 1차 결론을 낸다.
