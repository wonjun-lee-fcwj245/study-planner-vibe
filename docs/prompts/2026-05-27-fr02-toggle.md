## 교훈 (이 프롬프트 경험에서 배운 것)

### 1. LLM이 기존 코드를 한 줄도 안 바꿨다 — 본 과제 분석 주제의 첫 검증
오늘의 가장 중요한 관찰: LLM이 어제 코드의 createTask, addTask, escapeHtml 등을 **한 줄도 손대지 않았다.**
일반적으로 LLM은 "더 좋아 보이게" 기존 코드도 수정하려는 경향이 있다.
오늘 그게 발생하지 않은 이유는 프롬프트에 "어제 만든 함수와 변수명을 그대로 사용"이라고 **명시적**으로 적었기 때문이다.

**핵심 교훈**: LLM이 기존 코드를 보존하느냐는 LLM의 능력이 아니라 프롬프트의 명시성에 달려 있다.
"바꾸지 마" 한 줄을 명시하면 LLM이 그걸 가드레일로 인식한다. 명시하지 않으면 자발적으로 리팩토링한다.
→ 보고서 6.3절(구현 단계의 교훈)에 **"LLM 자발 리팩토링의 제어 방법"** 사례로 인용.

### 2. 자발 추가 두 번째 관찰: CSS transition
어제 escapeHtml에 이어, 오늘은 LLM이 CSS에 `transition` 속성을 자발적으로 넣었다.
"상태 변화 시 부드러운 전환"이라는 주석까지 달아서.
SRS 정합성 검토: NFR-02(반영 200ms 이내)와 정합한다 — 0.2초 전환이라 200ms 한도 안.
**채택, 다만 회고에서 "자발 추가 #2"로 기록.**

자발 추가가 누적되면 패턴이 보일 것이다. 지금까지의 패턴:
- 자발 추가 #1 (Day 8): escapeHtml — 보안, NFR-06 정합
- 자발 추가 #2 (Day 9): CSS transition — UX, NFR-02 정합
**둘 다 NFR 정합이라는 공통점**이 흥미롭다. LLM이 비기능 요구를 자발적으로 보완하는 경향이 있는 듯.

### 3. 첫 시도 채택률이 또 100%
FR-01에 이어 FR-02도 첫 시도 채택. 가설 검증의 두 번째 데이터 포인트.
이터레이션 1 회고에서 4건 모두 첫 시도 채택이면, 그 자체가 보고서의 강력한 사례다.
다만 모든 게 첫 시도 채택이면 "프롬프트가 너무 쉽거나 LLM이 너무 똑똑한 것 아닌가"라는
역방향 의심도 가능하다. FR-04(localStorage)나 이터레이션 2의 차트 같은 어려운 작업에서
재현되는지가 진짜 검증이다.

### 4. 안티 패턴 발생: 0건
AP-1~AP-10 어느 항목에도 해당되지 않음.

특히 AP-2("전체 코드 다시 써줘")를 의식적으로 피했다. 어제 만든 함수를 그대로 두고
변경된 부분만 출력하라고 명시했기 때문이다. 이게 점진성 원칙의 직접 적용.

### 5. 이번 프롬프트의 길이가 어제보다 짧아진 이유
어제 프롬프트는 약 40줄, 오늘은 약 35줄. 짧아진 부분은 [맥락] — 어제 모두 정의된 내용을
이미 인지하고 있는 LLM에게 다시 길게 설명할 필요가 없었다.

**프롬프트의 길이는 작업 복잡도가 아니라 사전 맥락의 누적도에 반비례한다.**
이터레이션이 진행될수록 프롬프트가 짧아져도 되는 이유. 단, 새 채팅을 열면 다시 길어진다.
이게 Day 7에 결정한 "본 채팅을 그대로 이어가기" 운영 규칙의 직접 효과다.
