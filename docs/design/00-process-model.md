# 프로세스 모델 선정 (Process Model Selection)

> **결정일**: 2026-5-18
> **결정자**: 이원준

## 1. 후보 모델 비교

| 모델 | 장점 | 단점 | 바이브코딩 적합성 |
|------|------|------|----------------|
| 폭포수 (Waterfall) | 단계가 명확, 문서화 강제 | 요구사항 변경 대응 어려움, 후반에 위험 집중 | ✗ 낮음 |
| V-모델 | 검증·확인이 단계별 명확 | 폭포수의 단점 그대로 | △ 중간 |
| 프로토타이핑 | 빠른 시각적 피드백 | 프로토타입을 본 제품으로 착각하기 쉬움 | ○ 높음 |
| **반복적/점진적 (Iterative)** | **점진적 개선, 회고로 학습** | **계획 오버헤드** | **◎ 매우 높음** |
| 애자일/Scrum | 변화 대응 우수 | 1인·20일에는 과한 의례 | ○ 높음 (간소화 필요) |

## 2. 선정 결정

**채택 모델: 반복적/점진적 개발 (3 iterations)**

### 선정 근거

1. **바이브코딩 특성과의 정합성**: 바이브코딩은 LLM과의 빠른 대화 사이클로 코드를 생산한다.
   "한 번에 완벽한 명세 → 한 번에 완벽한 코드"는 바이브코딩의 본질과 어긋난다.
   짧은 사이클을 반복하며 프롬프트 품질을 개선하는 흐름이 가장 자연스럽다.

2. **시간 제약과의 정합성**: 개발 기간이 짧기 때문에,
   실패 시 회복 시간이 없다. 3회 분할은 각 회차마다 "동작하는 버전"을 확보한다.

3. **회고의 가치**: 본 과제의 핵심은 "프로세스 적용의 교훈"을 도출하는 것이다.
   매 이터레이션 종료 시점의 KPT 회고는 그 자체로 보고서의 1차 자료가 된다.

4. **위험 분산**: MVP를 일찍 확보하면, 후반에 문제가 생겨도 최소 v0.1은 제출 가능하다.

## 3. 이터레이션 구조

```
[도입]            [정련]            [구축 — 3 iterations]                    [전환]
Day 1~4    →    Day 5~7    →   IT1(8~11) → IT2(12~15) → IT3(16~18)   →   Day 19~20
요구사항 분석    설계·전략     MVP          기능 확장      품질·테스트       보고서

각 이터레이션 내부 사이클:
  요구사항 확정 → 설계 보완 → 바이브코딩 구현 → 테스트 → 회고
```
