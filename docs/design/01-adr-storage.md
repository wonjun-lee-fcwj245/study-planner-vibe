# ADR-001: 데이터 저장 방식으로 localStorage 채택

## 상태 (Status)
채택됨 (Accepted)

## 일자
2026-05-22

## 맥락 (Context)

학습 플래너는 사용자의 학습 항목, 완료 상태, 과목, 생성일 등의 데이터를 영속적으로 보관해야 한다 (FR-04).
이 데이터는 새로고침이나 브라우저 종료 후에도 유지되어야 하지만, 본 버전에서 다중 기기 동기화는
Out of Scope으로 결정한 상태다 (비전 문서, SRS 1.2절).

또한 NFR-06에 따라 외부 서버로 개인 학습 데이터를 전송하지 않아야 한다. 이는 페르소나 2(박지훈)의
"가입 없이 즉시 시작 가능" 요구와도 맞물린다.

기술 제약으로는 프로젝트 시간 제약이 있어, 백엔드 구축이나 복잡한 데이터 계층 도입은
ROI가 매우 낮다.

## 검토한 대안 (Options Considered)

### 옵션 A: localStorage

- **장점**:
  - 별도 설정 없이 즉시 사용 가능
  - 브라우저 표준 API로 모든 타깃 브라우저에서 동작
  - 동기 API라 코드가 단순함
  - NFR-06(외부 전송 없음)을 자연스럽게 만족
- **단점**:
  - 용량 제한 (도메인당 약 5~10MB)
  - 문자열만 저장 가능 (객체는 JSON 직렬화 필요)
  - 단일 기기·단일 브라우저로 데이터 격리

### 옵션 B: IndexedDB

- **장점**:
  - 큰 용량, 객체 직접 저장, 인덱스·쿼리 지원
  - 비동기 API로 메인 스레드 블로킹 없음
- **단점**:
  - API가 복잡하고 verbose
  - 본 버전의 데이터 규모(예상 수백 건 이내)에 과한 도구

### 옵션 C: 백엔드 + DB (Node + SQLite 등)

- **장점**:
  - 다중 기기 동기화 가능
  - 데이터 백업·복구 용이
- **단점**:
  - 서버 호스팅, 인증, API 설계 필요 — 본 과제 시간 안에 불가
  - NFR-06(외부 전송 없음) 위배
  - 비전 문서의 "즉시성" 가치(가입·설치 없이 사용)와 충돌

### 옵션 D: 파일 다운로드/업로드 기반 (JSON 파일)

- **장점**: 사용자가 데이터 완전 통제
- **단점**: 매번 파일을 직접 관리해야 해서 페르소나 1(이원준)의 "30초 이내 확인" 사용 맥락과 충돌

## 결정 (Decision)

**옵션 A (localStorage)를 채택한다.**

핵심 근거는 세 가지다.

첫째, 본 버전의 데이터 규모(학습 항목 수백 건)와 사용 패턴(단일 사용자, 단일 기기)이 localStorage의 한계 안에 충분히 들어온다.

둘째, IndexedDB의 추가 능력(큰 용량, 쿼리)은 현재 요구사항에서 필요 없다. YAGNI 원칙에 따라 가장 단순한 도구를 선택한다.

셋째, 비전 문서의 "즉시성" 가치와 NFR-06(외부 전송 없음)을 동시에 만족하는 유일한 옵션이다.

## 결과 (Consequences)

### 긍정적
- 첫 코드 작성부터 데이터 영속성 확보 (의존성 0개)
- 바이브코딩 프롬프트가 단순해진다 ("localStorage에 저장"이라는 한 줄로 명확)
- 비동기 처리 없이 직관적인 코드 구조 가능

### 부정적 / 트레이드오프
- 다중 기기 사용자의 데이터가 동기화되지 않는다 — 페르소나 1(이원준)의 "노트북·집 데스크톱 오감" 맥락과 일부 충돌
- 브라우저 데이터 정리 시 사용자가 데이터 손실 위험을 진다
- 약 5~10MB 한도를 초과하면 동작 보장 어려움 (현실적으로는 도달 불가)

### 후속 영향
- **영향받는 코드**: 추후 작성될 `src/app.js`의 모든 데이터 입출력 함수
- **영향받는 FR**: FR-04 (직접 구현 대상), FR-13 (Won't 처리로 결론 — localStorage가 유일 저장소이므로 내보내기/가져오기의 실용성 낮음)
- **재검토 시점**: 다음 버전(v2.0)에서 다중 기기 동기화 요구가 생기면 본 ADR을 폐기하고 백엔드 + IndexedDB 캐시 조합 ADR로 대체한다.
