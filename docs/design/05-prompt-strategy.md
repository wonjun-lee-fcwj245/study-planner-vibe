# 바이브코딩 프롬프트 전략 (Prompt Strategy)

> **버전**: 1.0
> **작성일**: 2026-05-25
> **참조 문서**: SRS 0.3, ADR-001, ADR-002, 03-wireframes 0.1, 04-data-model 0.1
> **메타 NFR 연결**: MNFR-01 (FR ID 인용), MNFR-02 (100% 이해)

## 1. 문서 목적

본 문서는 **본 과제의 가장 차별화된 산출물**이다.

일반적인 "프로세스에 입각한 개발"이라면 SRS·ADR·와이어프레임으로 충분하다.
하지만 본 과제는 "프로세스에 입각한 **바이브코딩**"이다.
바이브코딩의 입력은 코드가 아니라 **프롬프트**다.
따라서 프롬프트 자체를 설계하지 않으면, "프로세스 적용"이라는 표현은 절반에 그친다.

본 문서는 다음을 정의한다.
1. 사용할 LLM과 그 선정 근거
2. 프롬프트가 따라야 할 5가지 원칙
3. 표준 프롬프트 템플릿
4. 의도적으로 피할 안티 패턴
5. 프롬프트 로그 양식

이 문서가 Day 8 이후 모든 바이브코딩 행동의 기준이 된다.

## 2. 사용할 LLM과 선정 근거

### 2.1 선정 도구 — 확정

**확정 결정: Claude (claude.ai 웹 인터페이스)**

본 결정은 Day 7(2026-05-25) 작업 중 명시적으로 확정되었다.
이후 본 과제의 모든 바이브코딩 프롬프트는 본 도구로 진행한다.

### 2.2 검토한 대안

| 도구 | 장점 | 단점 | 채택 여부 |
|------|------|------|----------|
| **Claude (웹)** | 긴 맥락 처리 우수, 채팅 단위 토의 보존, 우리 문서들이 이미 대화 흐름에 있음 | 코드 자동 적용은 수동 복사 필요 | **채택** |
| Claude Code (CLI) | 강력한 코드 편집 능력, 자동 파일 수정 | 자동 적용이 MNFR-02 운영에 의식적 추가 절차 필요 | 미채택 |
| ChatGPT | 보편적, 익숙함 | 본 과제의 토의 맥락과 분리됨 | 미채택 |
| GitHub Copilot | IDE 통합, 빠른 자동완성 | 자동완성 중심으로 "프롬프트" 개념이 약함 — 본 과제의 분석 대상으로 부적합 | 미채택 |
| Cursor | 강력한 코드 편집 능력 | 자동 리팩토링이 프롬프트→결과의 인과를 흐리게 만듦 | 미채택 |

### 2.3 채택 결정의 근거

세 가지다.

**첫째, 맥락 연속성.** Day 1~6 동안 작성한 모든 설계 문서(SRS, ADR, 와이어프레임, 데이터 모델)가
이미 Claude와의 대화 흐름 안에 있다. 새 도구로 옮기면 모든 맥락을 다시 전달해야 한다.
이는 MNFR-01(FR ID 인용)을 적용하기 어렵게 만든다.

**둘째, 프롬프트-결과 추적성.** 본 과제는 "어떤 프롬프트가 어떤 결과를 만들었는가"를 보고서에서
분석한다. Cursor나 Copilot은 자동 적용·자동 리팩토링으로 인과 관계가 흐려진다.
Claude 웹 인터페이스는 한 메시지 = 한 프롬프트 = 한 응답이라는 명확한 단위가 있다.

**셋째, MNFR-02(100% 이해) 준수 용이성.** IDE 통합 도구나 CLI는 코드가 자동 적용되어
"보지 않고 채택"하는 유혹이 강하다. Claude 웹에서는 응답을 읽고, 검토하고, 손으로 복사하는
과정이 자연스러운 절차로 들어간다. **이 수동 복사 절차 자체가 100% 이해를 강제하는 가드레일이다.**

### 2.4 채택의 운영 규칙

본 결정에 따라 다음 운영 규칙을 확정한다.

1. **본 과제의 모든 바이브코딩 프롬프트는 Claude 웹에서 진행한다.** Claude Code, ChatGPT 등 다른 도구는 사용하지 않는다.
2. **본 채팅 세션(Day 1부터 시작된 토의)을 그대로 이어간다.** 새 채팅을 열지 않는다 — 맥락 단절 방지.
3. **응답 코드는 항상 수동으로 복사하여 적용한다.** 자동 적용 기능을 사용하지 않는다 (MNFR-02 가드레일).
4. **각 프롬프트와 응답은 `docs/prompts/`에 즉시 로그한다.** 채팅 히스토리에만 의존하지 않는다.

## 3. 프롬프트 원칙 (5가지)

본 프로젝트의 모든 바이브코딩 프롬프트는 다음 5가지 원칙을 따른다.
이 원칙들은 MNFR-01과 MNFR-02를 운영 가능한 규칙으로 변환한 것이다.

### 원칙 1: 맥락 우선 (Context First)
모든 프롬프트는 최소한의 맥락 문장으로 시작한다.

> *"학습 플래너 v0.1 MVP 구현 중. 순수 HTML/CSS/JS (ADR-002), localStorage 사용 (ADR-001).
> 현재 `src/app.js`에 빈 Task 배열만 정의된 상태."*

이 한 문장이 LLM의 응답 품질을 크게 좌우한다. 맥락 없는 프롬프트는 LLM이 자기 기본 가정으로
빈칸을 채우게 만들고, 그 가정이 본인의 의도와 어긋날 가능성이 높다.

**본 과제에서는 채팅 연속성으로 맥락이 어느 정도 자동 유지되지만, 그래도 매 프롬프트마다
간략한 맥락 문장을 적는다.** 이는 프롬프트 로그를 단독으로 읽을 때 평가자가 이해할 수 있게
하기 위함이다.

### 원칙 2: 요구사항 ID 인용 (Cite FR IDs)
구현 요청 시 SRS의 FR-XX 번호를 명시적으로 인용한다.

> ❌ "학습 항목 추가 기능 만들어줘"
> ✓ "FR-01(학습 항목 추가)을 구현해줘. SRS의 UC-01 기본 흐름 1~7을 참고."

이는 MNFR-01의 직접 적용이다. FR ID를 인용하면 두 가지가 일어난다.
- LLM이 정확히 그 FR의 정의를 따른다 (대체 흐름까지 고려)
- 프롬프트 로그에서 "이 코드는 어느 FR의 산출물인가"가 자동으로 추적된다

### 원칙 3: 단일 책임 (Single Responsibility per Prompt)
하나의 프롬프트에 하나의 기능만 요청한다. 여러 기능을 묶지 않는다.

> ❌ "FR-01, FR-02, FR-03 한 번에 구현해줘"
> ✓ "먼저 FR-01만 구현해줘. FR-02, FR-03은 그 다음에."

복합 요청은 응답이 길어지고, 각 기능의 책임이 섞이며, 디버깅이 어려워진다.
또한 본인이 LLM 응답을 한 번에 100% 이해하기 어려워져 MNFR-02 위배 위험이 커진다.

### 원칙 4: 검증 기준 동봉 (Acceptance Criteria Inline)
"무엇이 완료인가"를 프롬프트 안에 명시한다.

> *"FR-04(데이터 영속성)를 구현해줘. 다음이 모두 동작해야 한다:
> 1. 항목 추가 후 새로고침해도 표시됨
> 2. 완료 상태가 새로고침 후에도 유지됨
> 3. localStorage 키는 `study-planner:tasks` (데이터 모델 04-data-model 4.2)"*

검증 기준이 명시되면 LLM이 "동작하는 것 같은 코드"가 아니라 "검증 가능한 코드"를 만든다.
또한 본인이 응답을 평가할 객관적 기준이 생긴다.

### 원칙 5: 기록 의무 (Logging Discipline)
모든 프롬프트와 응답은 `docs/prompts/YYYY-MM-DD-기능명.md`에 저장한다.
실패한 시도도 지우지 않는다. 시도 1, 시도 2, 시도 3... 모두 보존한다.

**실패한 프롬프트가 보고서의 가장 좋은 사례다.** "잘 안 됐던 프롬프트"가 "잘 됐던 프롬프트"보다
lessons learned에 더 풍부한 자료를 제공한다.

## 4. 표준 프롬프트 템플릿

원칙 1~4를 운영하기 위한 템플릿이다. 모든 구현 프롬프트는 이 구조를 따른다.

```
[맥락]
프로젝트: 학습 플래너 (Study Planner)
현재 이터레이션: N
현재 파일 상태: (간단히)
관련 ADR/문서: ADR-XXX, 04-data-model 등

[요청]
구현할 FR: FR-XX
구현할 UC: UC-XX (기본 흐름 X~Y번)
요청 내용: (구체적으로)

[제약]
- 사용 가능 기술: 순수 HTML/CSS/JS (ADR-002)
- 데이터: study-planner:tasks 키의 localStorage (ADR-001, 04-data-model 4.2)
- 사용 금지: 외부 라이브러리, 빌드 도구
- 파일 구조: src/index.html, src/style.css, src/app.js

[검증 기준]
완료 조건:
1. (관찰 가능한 동작)
2. (관찰 가능한 동작)
3. ...

[원하는 출력 형식]
- 변경할 파일과 변경 위치 명시
- 코드 + 한 줄 설명 주석
- 변경 사항 요약 (어떤 함수가 추가/수정됐는가)
```

### 4.1 채워진 예시

> **[맥락]**
> 프로젝트: 학습 플래너 (Study Planner) — v0.1 MVP 작업 중.
> 현재 이터레이션: 1.
> 현재 파일 상태: `src/index.html`은 빈 골격, `src/app.js`는 비어있음.
> 관련 문서: ADR-001 (localStorage), ADR-002 (Vanilla JS), 04-data-model (Task 객체 구조).
>
> **[요청]**
> 구현할 FR: FR-01 (학습 항목 추가).
> 구현할 UC: UC-01 기본 흐름 1~7번.
> 요청 내용: 입력 필드 + 추가 버튼 + 메모리 상의 tasks 배열에 추가하는 로직까지.
> localStorage 저장은 FR-04에서 별도로 추가할 것이므로 지금은 메모리만.
>
> **[제약]**
> - 순수 JS, 외부 라이브러리 금지
> - Task 객체는 04-data-model 3.1의 6개 필드를 가져야 함
> - id 생성은 `crypto.randomUUID()` 사용
> - 입력이 비면 추가 버튼 비활성화 (UC-01 대체 흐름 4a)
>
> **[검증 기준]**
> 1. 텍스트 입력 후 Enter 또는 추가 버튼 → 화면에 항목 표시
> 2. 입력 필드가 비워짐
> 3. 빈 입력 시 추가 버튼 비활성화
> 4. id, createdAt이 자동 부여되어 콘솔에서 확인 가능
>
> **[원하는 출력 형식]**
> - `src/index.html`의 변경 사항 (어디에 입력 영역 추가)
> - `src/app.js`의 변경 사항 (어떤 함수 추가)
> - 변경 후 한 줄 설명

## 5. 안티 패턴 (피해야 할 프롬프트)

본 프로젝트에서 의도적으로 **피하기로** 한 프롬프트 유형이다.
회고에서 이 목록과 실제 사용 프롬프트를 비교하여, 안티 패턴에 빠진 사례를 추적한다.

| # | 안티 패턴 | 왜 나쁜가 | 어떻게 고치는가 |
|---|-----------|----------|---------------|
| AP-1 | "학습 플래너 만들어줘" | 맥락·요구사항 0, LLM의 자기 가정으로 채워짐 | 원칙 1, 2 적용 |
| AP-2 | "전체 코드 다시 써줘" | 점진성 파괴, 본인이 못 따라감 | 단위 기능별 요청 |
| AP-3 | "버그 고쳐줘" | 재현 절차·기대 동작 누락 | 증상·재현·기대 명시 |
| AP-4 | "FR-01, FR-02, FR-03 다 해줘" | 원칙 3 위배 | 한 번에 하나씩 |
| AP-5 | "이거 더 잘 만들어줘" | "잘"의 정의 없음 | 구체적 개선 기준 명시 |
| AP-6 | "그냥 알아서 해줘" | LLM이 친절하게 범위 부풀림 (FWC-001 사례) | SRS 인용 |
| AP-7 | "React로 다시 짜줘" | ADR-002 위배 | ADR 확인 후 결정 |
| AP-8 | "이 라이브러리 써봐" | 검토 없는 의존성 도입 | 새 ADR 작성 후 결정 |
| AP-9 | "코드만 줘, 설명 빼고" | MNFR-02 위배 — 이해 없이 채택 | 설명 요청 유지 |
| AP-10 | "내가 좋아할 만한 디자인으로" | 와이어프레임 무시 | 와이어프레임 인용 |

### 5.1 안티 패턴 자가 점검 절차

프롬프트를 작성한 뒤, 보내기 전에 다음을 자문한다.

1. 맥락이 한 문장 이상 있는가? (원칙 1)
2. FR ID 또는 문서 ID를 인용했는가? (원칙 2)
3. 한 가지 기능만 요청하는가? (원칙 3)
4. "완료" 기준이 명확한가? (원칙 4)
5. 위 안티 패턴 10개 중 어느 것에도 해당되지 않는가?

5개 중 1개라도 미달이면 프롬프트를 다시 작성한다.

## 6. 응답 수용 절차 (MNFR-02 운영)

LLM 응답을 받은 후, 코드를 채택하기 전 다음 절차를 거친다.

### 6.1 4단계 점검

1. **읽기**: 응답 전체를 처음부터 끝까지 한 번 읽는다. 스크롤만 내리지 않는다.
2. **이해**: 각 함수가 무엇을 하는지 한 줄로 자신 있게 설명할 수 있는가? 못 하면 LLM에게 다시 묻는다.
3. **검증 매핑**: 응답 코드가 프롬프트의 검증 기준을 어떻게 만족하는지 1:1로 짚는다.
4. **반영**: 위 3단계 모두 통과 시 코드를 **수동으로** 복사하여 적용.

**중요**: 4단계 "반영"은 항상 수동 복사다. Claude 웹의 코드 블록을 본인이 직접 선택·복사하여
에디터에 붙여넣는다. 이 절차 자체가 MNFR-02의 운영 가드레일이다 (2.3절 세 번째 근거 참조).

### 6.2 100% 이해 못한 경우의 처리

만약 어떤 함수를 100% 이해하지 못한 채로 시간 부족으로 채택해야 한다면:

```javascript
// TODO: 미이해 — LLM 코드, 동작 원리 추후 학습 필요
//   요청 프롬프트: docs/prompts/2026-XX-XX-... 시도 N
//   이해 못한 부분: (구체적으로)
function complexFunction() { ... }
```

이런 주석을 단다. 그리고 그 날 일지의 lessons learned에 "이해 못한 코드 채택" 항목을 추가한다.
**이런 사례가 보고서의 핵심 자료다** — 바이브코딩의 한계가 어떻게 발현되는지 직접 증거.

이터레이션 회고에서는 `// TODO: 미이해` 주석을 grep으로 카운트한다. 그 수치가 본 과제
lessons learned 4번째 항목("AI 코드를 이해하지 못한 채 쌓일 때의 리스크")의 정량 지표다.

## 7. 프롬프트 로그 양식

`docs/prompts/YYYY-MM-DD-기능명.md` 파일은 다음 구조를 따른다.

```markdown
# 프롬프트 로그: [기능명]

## 메타 정보
- 일자: YYYY-MM-DD
- 관련 요구사항: FR-XX (관련 UC 함께)
- 사용 LLM: Claude (claude.ai 웹)
- 총 시도 횟수: N

## 시도 1
### 프롬프트
(전문을 그대로 붙여넣기)

### 응답 요약
- LLM이 무엇을 만들었는가 (3~5줄)
- 코드 분량: 약 N줄
- 변경 파일: src/...

### 평가
- 잘된 점:
- 부족한 점:
- 채택 여부: 채택 / 부분 채택 / 거절

## 시도 2 (실패 시 또는 개선 시)
### 프롬프트 (이전과의 차이만)
(이전 프롬프트 대비 무엇을 바꿨는가)

### 응답 요약
...

### 평가
...

## 최종 채택 코드
- 파일: src/app.js
- 함수: addTask(), renderTasks()
- 줄 수: 추가 N줄, 수정 M줄

## 교훈 (이 프롬프트 경험에서 배운 것)
- (보고서 lessons learned의 원자료)
```

### 7.1 양식의 핵심: "시도 N"

본 양식의 가장 중요한 부분은 **여러 시도를 모두 보존**하는 것이다.
첫 시도에 성공하는 경우는 드물다. 시도 1이 어떻게 부족했고, 시도 2에서 무엇을 바꿨는지가
바이브코딩의 핵심 학습이다.

만약 첫 시도에 성공했다면 그 자체가 분석거리다 — "왜 첫 시도에 성공했는가?"는
"잘 만든 프롬프트의 특징"으로 보고서에 인용된다.

각 프롬프트 로그에 다음 시간을 측정한다 (1분 단위).

| 단계 | 시간 |
|------|------|
| 프롬프트 작성 시간 | |
| LLM 응답 대기 시간 | |
| 응답 검토 시간 | |
| 코드 적용 시간 | |
| 디버깅·수정 시간 | |
| **총 소요 시간** | |

이 데이터가 보고서 5.1절(정량적 분석)의 핵심 표를 만든다.
"바이브코딩이 정말 빨랐는가, 정확히 얼마나 빨랐는가"를 답할 수 있는 유일한 방법이다.

## 9. 비-구현 프롬프트의 처리

본 문서는 주로 "구현" 프롬프트를 다뤘다. 하지만 바이브코딩 중에는 다른 종류의 프롬프트도 발생한다.

| 프롬프트 유형 | 처리 방식 |
|--------------|----------|
| 구현 (코드 생성) | 본 문서 표준 템플릿 사용, 로그 작성 |
| 디버깅 | 증상·재현·기대를 명시한 별도 양식 (시도별 로그는 동일) |
| 설명 요청 (코드 이해) | 일지의 "AI 토의 발췌" 절에 기록, 별도 로그 X |
| 리팩토링 | 구현 프롬프트와 동일 양식 + "기존 코드 어느 부분 바꾸는지" 명시 |
| 설계 토의 | 일지의 "AI 토의 발췌" 절에만 기록 |

설명 요청·설계 토의는 코드를 만들지 않으므로 프롬프트 로그가 아니라 일지에 들어간다.
하지만 디버깅과 리팩토링은 코드를 변경하므로 프롬프트 로그에 포함한다.

## 10. 본 전략의 평가 기준

이터레이션 1 회고(Day 11) 시점에 본 전략 자체를 평가한다.

| 평가 항목 | 측정 방법 | 목표 |
|----------|----------|------|

| 시도당 평균 채택률 | 시도 횟수 vs 채택 수 | 60% 이상 |
| `// TODO: 미이해` 주석 수 | grep | 5개 이하 |

본 평가 결과 자체가 lessons learned 자료다. 목표 달성 여부와 무관하게,
"왜 그렇게 됐는가"의 분석이 보고서의 6.3절(구현 단계의 교훈)을 채운다.
