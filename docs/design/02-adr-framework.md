# ADR-002: 프레임워크 없이 순수 HTML/CSS/JS 채택

## 상태 (Status)
채택됨 (Accepted)

## 일자
2026-05-22

## 맥락 (Context)

학습 플래너는 단일 페이지 형태의 가벼운 웹 애플리케이션이다. 본 과제는 시간 제약이 있음.

본 과제의 진짜 평가 대상은 **"프로세스에 입각한 바이브코딩의 효과 분석"** 이지 "프레임워크 선택의 멋짐"이 아니다.
따라서 프레임워크 선택의 기준은 "기술의 트렌디함"이 아니라 **"프로세스 적용 시간을 최대화할 수 있는가"** 다.

또한 비전 문서의 "즉시성" 가치(가입·설치 없이 즉시 사용)는 결과물뿐 아니라 개발 환경에도 적용된다.
복잡한 빌드 도구는 첫날부터 환경 설정에 시간을 통째로 소비하게 만들 위험이 있다.

## 검토한 대안 (Options Considered)

### 옵션 A: 순수 HTML/CSS/JS (Vanilla)

- **장점**:
  - 환경 설정 0분, 즉시 시작 가능
  - 빌드 도구 불필요 → `index.html`을 더블 클릭해서 실행 가능
  - GitHub Pages 즉시 배포 가능
  - 학습 비용 없음 — 본인의 기존 지식으로 충분
  - 바이브코딩 결과물을 본인이 100% 이해할 수 있다 (MNFR-02 만족 용이)
- **단점**:
  - 컴포넌트 재사용성이 낮음
  - 상태 관리를 직접 구현해야 함
  - 코드량이 늘어나면 구조 관리가 어려워질 수 있음

### 옵션 B: React (Create React App / Vite)

- **장점**:
  - 컴포넌트 기반 구조로 가독성 좋음
  - useState/useEffect로 상태 관리 직관적
  - 모던 웹 개발 표준
- **단점**:
  - 환경 설정에 첫날 많은 시간 소모 가능 (Node 설치, 패키지 설치, 빌드 도구 학습)
  - 번들링·HMR·라우터 등 부수 학습 비용
  - 본 프로젝트 규모(단일 페이지, 수백 줄)에 비해 과한 도구
  - 본인이 100% 이해 못 한 코드(빌드 결과물, 가상 DOM 동작)가 많아져 MNFR-02 위배 위험

### 옵션 C: Vue / Svelte / Solid

- **장점**: React보다 학습 비용이 다소 낮을 수 있음
- **단점**: React와 같은 환경 설정 부담, 본인 익숙도가 React보다 낮을 가능성

### 옵션 D: jQuery

- **장점**: DOM 조작 간소화
- **단점**: 2026년 시점에 사용 이유 약함, 모던 브라우저 API로 충분

## 결정 (Decision)

**옵션 A (순수 HTML/CSS/JS)를 채택한다.**

핵심 근거는 네 가지다.

첫째, **시간 제약 해소.** 환경 설정 시간을 0으로 만들어, 요구사항 분석과 회고에 더 많은 시간을 투자할 수 있다.
본 과제의 평가는 코드의 모던함이 아니라 프로세스 적용 경험이다.

둘째, **MNFR-02(100% 이해) 준수 용이성.** Vanilla JS 코드는 한 줄 한 줄 본인이 추적할 수 있다.
React를 쓰면 LLM이 만든 useEffect 의존성 배열의 미묘한 동작을 본인이 못 따라잡을 위험이 있고, 그런 코드가 쌓이면 본 과제의 핵심 가설("프로세스 적용으로 바이브코딩의 한계 완화") 자체가 약해진다.

셋째, **즉시 배포 가능.** GitHub Pages에 자동 배포되어 평가자가 동작하는 결과물을 즉시 볼 수 있다.
별도 데모 영상 제작이 불필요하다.

넷째, **결과물의 단순성이 분석의 단순성을 보장한다.** 보고서 작성 시 "어떤 프롬프트가 어떤 코드를 만들어냈는가"를 명확히 추적하려면, 빌드 도구가 끼어들지 않는 게 좋다.

## 결과 (Consequences)

### 긍정적
- Day 8 바이브코딩 첫날에 환경 설정 0분
- 모든 코드가 본인 이해 범위 안에 있다 (LLM이 만든 클로저·이벤트 흐름까지 추적 가능)
- 코드 변경의 효과를 즉시 확인 (새로고침만)
- GitHub Pages 배포 자동 (별도 빌드 단계 없음)

### 부정적 / 트레이드오프
- 코드 재사용성이 React 컴포넌트만큼 깔끔하지는 않다
- 상태 관리 코드를 본인이 직접 구조화해야 한다 (이걸 잘하는 게 바이브코딩 능력의 테스트가 됨)
- 통계 차트 구현 시(FR-09) Chart.js CDN을 직접 가져와야 한다 — React 생태계의 컴포넌트 패키지처럼 매끄럽지는 않음

### 후속 영향
- **영향받는 코드**: 모든 `src/` 파일
- **영향받는 ADR**: 차트 라이브러리 도입 시 ADR-003에서 별도 결정 필요 (CDN 방식 등)
- **재검토 시점**: 만약 단일 페이지로는 관리가 어려운 규모(예: 1500줄 초과)에 도달하면 본 ADR을 부분 폐기하고 모듈화 또는 React 도입 ADR을 작성한다. 본 버전 안에서는 발생하지 않을 것으로 예상.
