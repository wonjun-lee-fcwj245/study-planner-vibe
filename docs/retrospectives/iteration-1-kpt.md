## 3. KPT 회고

### Keep (계속할 것)

**K1. 프롬프트 표준 템플릿 사용**
모든 4개 프롬프트가 [맥락]-[요청]-[제약]-[검증 기준]-[출력 형식] 구조를 따랐다.
이 구조 덕에 응답이 일관되게 정확했고, 검증 기준에 명시한 항목들은 거의 100% 반영됐다.
이터레이션 2에서도 유지.

**K2. FR ID 인용 (MNFR-01)**
모든 프롬프트가 FR-XX, UC-XX, ADR-XXX 등의 ID를 인용했다. 채팅 흐름이 길어졌어도
LLM이 정확한 문서를 참조할 수 있었다. 이게 응답 정확도의 주요 원인.

**K3. 수동 복사 절차 (Claude 웹 선정의 효과)**
Day 7에 결정한 "자동 적용 안 함, 수동 복사" 원칙이 4단계 점검(MNFR-02)을 자연스럽게 강제했다.
의식적 노력 없이 100% 이해를 유지함. 미이해 마커 0건이 그 증거.

**K4. 자발 추가의 SRS 정합성 판단**
LLM이 자발적으로 추가한 코드(escapeHtml, transition)를 무조건 받지도 거부하지도 않고
SRS 정합성으로 판단했다. 두 자발 추가 모두 NFR과 정합해서 채택. 이 판단 절차를 유지.

**K5. 일지에 AI 토의 발췌 보존**
매일 일지에 AI와의 토의를 기록한 게 의사결정 추적성을 만들었다. 어제 결정한 교훈이
오늘 의사결정에 즉시 활용되는 사례가 여러 번 발생했다 (예: Day 9 transition 채택 결정).

### Problem (문제가 된 것)

**P1. FR-04 시도 1에서 엣지 케이스 2개 누락 — 가장 중요한 데이터**
검증 기준에 명시했음에도 LLM이 누락했다. 이는 다음을 보여준다.
- 바이브코딩의 한계: 명시해도 누락 가능
- 그러나: 검증 기준이 있었기에 누락을 즉시 발견
- 검증 기준이 없었다면 출시 후 시크릿 모드 사용자가 버그를 만났을 것

**핵심 명제** (본 과제 가설의 정밀한 형태):
> 프로세스는 LLM의 누락을 막지 못한다. 그러나 누락을 즉시 발견하게 만든다.

**P2. 첫 시도 채택률이 너무 높아 분석 가치가 떨어질 뻔함**
FR-01, 02, 03이 모두 첫 시도 채택. 이대로 갔다면 보고서가 "프로세스 적용은 다 잘 됨"이라는
단순한 결론에 그쳤을 것이다.
Day 9 회고에서 "FR-04를 의도적으로 까다롭게"라고 결정한 게 분석 깊이를 확보했다.
**이터레이션 2에서도 일부 FR에 의도적으로 어려운 검증 기준을 도입해야 한다.**

**P3. 자가 테스트가 사후적**
이터레이션 중에 각 FR을 만들면서 즉시 동작 확인은 했으나, 전체 회귀 테스트는 Day 11에 몰렸다.
다행히 모두 통과했지만, 만약 회귀 버그가 발견됐다면 Day 11 시간이 부족했을 것이다.
이터레이션 2에서는 매일 회귀 체크를 미니 단위로 진행.

**P4. 자발 추가 누적 추적이 일관되지 않음**
Day 8, 9는 자발 추가를 추적했으나 Day 10에는 "발생 안 함"만 기록했다.
"발생 안 한 것"도 데이터다. 매 프롬프트 로그에 "자발 추가: 있음/없음 + 내용"을 정형 항목으로.

### Try (이터레이션 2에서 시도할 것)

**T1. 매일 회귀 체크 5분 루틴**
각 일자 시작 시 직전 기능이 그대로 동작하는지 5분 점검. P3 대응.

**T2. 자발 추가 정형 항목**
프롬프트 로그 양식에 "자발 추가" 절을 정형 항목으로 추가. 발생/미발생 모두 기록.

**T3. 일부 FR에 의도적 어려움 도입**
이터레이션 2의 FR-09(차트)에 의도적으로 까다로운 검증 기준 (예: 데이터 0건 시 빈 차트,
대용량 데이터 시 성능). P2 대응.

**T4. 보고서 골격에 정량 데이터 즉시 반영**
Day 7 회고의 Try 항목이었지만 실제로는 자주 빠뜨림. 매일 일지 마지막 5분에 강제 운영.

**T5. 이터레이션 1 회고 결과를 프롬프트 전략 문서에 반영**
05-prompt-strategy.md를 v1.1로 개정하여:
- 자발 추가 패턴 가설 추가
- "디버깅 프롬프트도 단일 책임 원칙 따른다" 명시 (FR-04 시도 2 사례)
- 본 회고에서 도출된 K1~K5를 "검증된 원칙"으로 격상

## 4. 프롬프트 효과 정성 분석

### 가장 효과적이었던 프롬프트
**FR-01 첫 프롬프트** (Day 8)

이유:
- 7일간의 모든 설계 문서를 명시적으로 인용 (ADR-001, ADR-002, 04-data-model, 03-wireframes)
- 검증 기준 5개를 관찰 가능한 동작으로 명시
- 첫 시도에 100% 검증 충족

**왜 잘 작동했는가**: 사전 설계가 프롬프트의 90%를 차지했다. LLM이 "맞춰서 가정"할 여지를 거의 남기지 않았다. **설계 시간 7시간이 첫 프롬프트 25분에서 회수된 직접 사례.**

### 가장 비효율적이었던 프롬프트
**FR-04 시도 1** (Day 10)

이유:
- 검증 기준 6개를 명시했음에도 엣지 케이스 2개 누락
- "어렵게 만들겠다"는 의도가 LLM의 happy path 우선 경향을 충분히 막지 못함

**무엇이 문제였는가**: 검증 기준을 적은 순서가 문제일 수 있다. "기본 동작 → 엣지 케이스" 순서로
적으면 LLM이 앞쪽에 집중한다. 다음엔 "엣지 케이스를 별도 강조 블록으로 분리"하거나 "엣지 케이스 먼저, 기본 동작 나중"으로 시도해볼 가치.

**그러나 이 실패가 본 과제에는 가장 가치 있는 데이터다.** 한계가 어떻게 발현되고 어떻게 발견되는지를 보여줬다.
